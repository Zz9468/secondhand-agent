# V2.1 统一账号与商品大厅升级计划

> 实施状态：七个阶段已完成。本文保留立项时的现状描述和设计推导，完成后的实际启动、接口与验收方式以 README 和 `docs/V2.1_验收清单.md` 为准。

## 一、版本定位

V2 已完成“访客买家议价 → 卖家审批 → Agent 通知 → 买家确认交易意向”的模式 B 闭环，但当前身份与入口仍是演示形态：买家使用自动签发的访客身份，卖家使用独立账号；买家打开页面后会自动选中第一个商品并创建或复用协商会话。

V2.1 在不改变价格规则、审批状态机、正式报价安全和交易意向确认语义的前提下，将系统升级为可由真实注册用户使用的统一入口：

- 一个用户只注册一个账号，不在注册时选择买家或卖家身份；
- 每个普通账号天然可以购买，也可以发布和管理自己的商品；
- “买家模式”和“卖家模式”只是当前界面与操作上下文，可以随时切换，不是固定角色；
- 买家先浏览卖家及商品，查看商品详情不会创建协商会话；
- 只有用户明确点击“与卖家协商”后，系统才创建或恢复该商品的协商会话；
- 卖家端只出现买家明确发起的协商，不再因打开网站产生空会话；
- 后端始终根据登录账号和资源归属校验权限，不能信任前端传入的用户身份或当前模式。

V2.1 是 V2 与既定 V3 之间的功能体验升级。V3 仍负责可靠性、可观测性和评测，V4 仍负责云服务器部署与运维。

## 二、已确认的产品决策

### 2.1 统一账号，不设置固定买卖角色

注册表单只收集用户名、显示名称和密码，不提供“买家/卖家”选择。账号登录后可以进入任一模式：

```text
打开网站
  ↓
注册 / 登录
  ↓
选择当前要做什么
  ├─ 我想买东西 → 买家商品大厅
  └─ 我要卖东西 → 卖家管理后台
                       ↕
                 随时切换模式
```

因此 V2.1 不建立 `user_roles` 表，也不把模式写入登录令牌。模式切换只改变前端路由和界面，服务端权限仍由当前账号、商品所有权和会话归属决定。

### 2.2 商品浏览与协商创建分离

买家浏览流程为：

```text
商品大厅 / 卖家列表
  ↓ 只读，不创建会话
商品详情 / 卖家公开主页
  ↓ 只读，不创建会话
点击“与卖家协商”
  ↓ POST 创建或复用会话
协商页面
```

以下行为都不得创建 `negotiation_sessions`：

- 打开网站或登录；
- 进入买家模式；
- 加载商品或卖家列表；
- 打开商品详情；
- 打开卖家公开主页；
- 刷新上述只读页面。

只有点击“与卖家协商”才调用创建接口。创建成功后跳转到会话页面；同一账号再次对同一商品发起协商时，应优先复用其仍为 `ACTIVE` 或 `WAITING_APPROVAL` 的会话。已经 `AGREED` 或 `CLOSED` 的历史会话不应被恢复为活动会话。

点击按钮代表买家已经明确发起协商，所以即使尚未发送第一条消息，该会话也可以出现在卖家协商列表中。若以后希望进一步减少零消息会话，可以另行改为“发送第一条消息时创建”，不在 V2.1 混用两种语义。

### 2.3 公开卖家页不是完整商户系统

V2.1 的“卖家/商户页面”是个人卖家的公开主页，展示公开显示名称和其已上架商品。它不包含企业认证、店铺装修、关注、评价、客服团队或商户组织权限。

公开接口不得返回用户名、密码哈希、私有协商规则、底价、自动接受阈值或其他卖家私有信息。用户名仅用于登录；公开页面使用 `display_name`。

## 三、目标页面与路由

V2.1 引入 Vue Router，将当前单文件中的买卖视图拆成明确页面：

| 路由 | 登录要求 | 作用 |
|---|---|---|
| `/` | 否 | 未登录时显示登录/注册入口；已登录时显示买家模式和卖家模式入口 |
| `/register` | 否 | 注册统一账号，不选择身份 |
| `/login` | 否 | 使用统一账号登录 |
| `/buyer` | 是 | 买家商品大厅，展示卖家和已上架商品 |
| `/sellers/:sellerId` | 是 | 卖家公开主页和该卖家的已上架商品 |
| `/products/:productId` | 是 | 商品公开详情，不创建协商会话 |
| `/buyer/negotiations` | 是 | 当前账号作为买家的协商历史 |
| `/negotiations/:sessionId` | 是 | 买家协商页面 |
| `/seller` | 是 | 当前账号的卖家工作台 |
| `/seller/products` | 是 | 发布、编辑、上下架自己的商品和配置私有策略 |
| `/seller/approvals` | 是 | 处理自己商品下的报价审批 |
| `/seller/negotiations` | 是 | 查看自己商品下的协商记录 |

顶部导航显示当前账号，并提供“买家模式 / 卖家模式”切换和退出。刷新具体路由后应保持当前页面，未登录访问受保护页面时跳转登录页，登录成功后返回原目标地址。

## 四、数据模型与迁移方案

### 4.1 统一账号表

将现有 `seller_accounts` 演进为统一的 `user_accounts`：

| 字段 | 说明 |
|---|---|
| `id` | 不可预测的账号 ID，主键 |
| `username` | 登录名，规范化后唯一，不通过公开接口暴露 |
| `display_name` | 对其他用户展示的名称 |
| `password_hash` | 带随机盐的不可逆密码哈希 |
| `is_active` | 账号是否可登录 |
| `created_at` / `updated_at` | 创建与更新时间 |

`products.seller_id` 和 `negotiation_sessions.buyer_id` 最终都引用 `user_accounts.id`。同一个账号既可以出现在商品的 `seller_id`，也可以出现在其他商品会话的 `buyer_id`。

### 4.2 现有数据兼容

迁移必须同时通过“现有 V2 数据库升级”和“空数据库从头升级”两条路径：

1. 现有卖家账号转换为统一账号，商品所有权保持不变；演示卖家的登录凭据继续由种子脚本设置，不把真实密码写入迁移。
2. 现有访客会话作为历史数据保留时，为其建立不可登录的历史账号映射，再为 `buyer_id` 建立外键；不能把多个旧访客错误合并成同一用户。
3. 新会话只允许绑定已登录且启用的统一账号。
4. 迁移完成前后，商品、报价、消息、审批和已达成意向的关联关系不能丢失。

如迁移实现采用“新增列 → 回填 → 切换读写 → 增加约束 → 删除旧列”的扩展/收缩方式，应在阶段提交中保留清晰的过渡边界，不能在同一版本中留下两套可被客户端任选的身份来源。

### 4.3 明确不新增角色表

V2.1 不需要 `user_roles`、`buyer_accounts` 或新的独立 `seller_accounts`。买卖模式不是授权角色。后续若增加平台管理员、审核员等真正具有不同权限的后台主体，再单独设计管理角色，不复用买卖模式概念。

## 五、后端接口规划

### 5.1 统一认证

| 方法 | 地址 | 作用 |
|---|---|---|
| `POST` | `/api/auth/register` | 注册统一账号并建立登录态 |
| `POST` | `/api/auth/login` | 统一账号登录 |
| `GET` | `/api/auth/me` | 获取当前账号的安全公开信息 |
| `POST` | `/api/auth/logout` | 删除统一登录 Cookie |

认证使用一个服务端签名的 HttpOnly Cookie。Cookie 只表达“当前是谁”，不包含买家或卖家模式。注册、登录和当前身份响应不得返回密码哈希。

### 5.2 买家大厅与公开信息

| 方法 | 地址 | 作用 |
|---|---|---|
| `GET` | `/api/products` | 获取已上架商品，可按卖家筛选 |
| `GET` | `/api/products/{id}` | 获取商品公开详情及卖家公开摘要 |
| `GET` | `/api/sellers` | 获取有已上架商品的卖家公开列表 |
| `GET` | `/api/sellers/{id}` | 获取卖家公开资料 |
| `GET` | `/api/sellers/{id}/products` | 获取该卖家的已上架商品 |
| `GET` | `/api/buyer/negotiations` | 获取当前账号作为买家的协商历史 |

商品列表、详情和卖家公开页均为只读，不得隐式调用协商创建逻辑。

### 5.3 显式发起协商

保留 `POST /api/negotiations` 作为“与卖家协商”按钮的唯一创建入口，但改为只接受已登录账号。服务端必须：

1. 校验商品存在且状态为 `AVAILABLE`；
2. 校验当前用户不是商品卖家，禁止与自己的商品协商；
3. 查找当前用户与该商品仍在进行的会话，有则复用；
4. 没有可复用会话时才创建新会话；
5. 返回 `session_id` 和 `created`，供前端跳转；
6. 使用数据库约束、事务锁或等效条件写入避免双击和并发请求生成两个活动会话。

原有消息、报价、审批、确认和关闭接口继续使用该会话，并将买家权限从访客 Cookie 改为统一账号 ID。所有卖家接口也改用同一个当前账号依赖，再通过商品所有权判断是否有权操作。

## 六、权限与安全边界

- 用户只能读取和操作 `buyer_id` 为自己的买家会话。
- 用户只能管理 `seller_id` 为自己的商品、策略、审批和卖家侧会话。
- 进入某个前端模式不会扩大权限；即使绕过页面直接调用 API，后端仍必须校验资源归属。
- 禁止用户对自己的商品创建协商，前端隐藏按钮只是体验优化，后端拒绝才是安全边界。
- 商品公开接口只能返回公开商品事实和卖家公开资料，不能返回私有价格规则。
- 卖家会话接口延续 V2 的隐私边界，不返回不必要的买家登录名和内部身份标识；只显示业务所需的买家公开名称时，也应通过专门字段返回。
- 注册接口需要校验用户名唯一性、密码强度和字段长度；错误响应不能泄露密码哈希、签名内容或数据库细节。
- 旧的访客签名 Cookie 和卖家专用 Cookie 在兼容迁移完成后停止作为授权来源，避免两套身份并存造成越权。

## 七、开发阶段

V2.1 采用“先统一身份底座，再改页面入口，最后切换会话创建语义”的顺序。每个阶段必须保持系统可运行，并在提交前完成受影响范围的自检。

| 阶段 | 主要工作 | 阶段完成标准 |
|---|---|---|
| 1. 统一账号数据模型与迁移 | 新增统一账号 ORM 与 Alembic 迁移；将现有卖家账号、商品外键和历史访客会话安全迁移到统一用户关系；更新种子数据，使演示账号仍可重复初始化。暂不改变现有页面入口。 | 现有 V2 数据库升级与空库全量升级都成功；商品、会话、消息、报价和审批关联不丢失；账号 ID 外键及唯一约束有效；迁移降级或回滚边界有测试。 |
| 2. 统一注册、登录与权限依赖 | 实现注册、统一登录、当前账号和退出接口；将买家与卖家 API 改为同一个 `get_current_user` 身份依赖，再分别校验买家会话归属和卖家商品所有权；停止信任旧访客及卖家专用 Cookie。 | 新用户可以注册、登录和退出；同一登录态可访问自己的买家和卖家资源；未登录、跨买家、跨卖家、禁用账号及伪造旧 Cookie 均被拒绝；原 V2 业务 Service 回归通过。 |
| 3. 前端路由与统一入口 | 引入 Vue Router，拆分登录、注册、模式选择和受保护页面框架；建立最小当前账号状态管理、登录后原路返回、刷新恢复及买卖模式切换。此阶段可先复用现有买家和卖家组件。 | 注册和登录不要求选择身份；登录后可进入任一模式并随时切换；直接访问和刷新受保护路由行为正确；退出后不能继续访问受保护页面；前端类型检查与生产构建通过。 |
| 4. 买家商品大厅与卖家公开页 | 建立商品大厅、商品详情、卖家列表和卖家公开主页；公开响应补充安全的卖家摘要；删除买家页面自动选择第一个商品并创建会话的行为。 | 打开、浏览、切换和刷新商品/卖家页面时，数据库不会新增协商会话；买家看不到底价、自动接受阈值、登录名和密码字段；商品详情能正确展示卖家及公开商品信息。 |
| 5. 显式发起协商与买家会话中心 | 在商品详情增加“与卖家协商”按钮；后端创建接口绑定当前账号，禁止自我协商，并保证同一用户与商品最多复用一个进行中会话；新增买家协商历史和会话恢复入口，协商页面改为按路由参数加载。 | 只有点击按钮才创建或复用会话；双击、重复请求和并发请求不会产生重复活动会话；卖家只在明确发起后看到记录；不同账号不能读取彼此会话；原聊天、报价、审批和确认闭环正常。 |
| 6. 卖家工作台整合 | 将现有商品管理、审批和协商列表迁入统一路由及账号体系；补充无商品、无审批、无会话等空状态；统一公开显示名称和模式切换；清除前端对演示卖家及双 Cookie 的依赖。 | 任一注册账号都能发布并管理自己的商品，也能切换到买家模式浏览他人商品；不能编辑、审批或查看他人的卖家资源；自己商品不显示协商入口；已有 V2 审批流程和轮询生命周期不回归。 |
| 7. 全量回归、兼容清理与验收 | 删除不再使用的访客认证接口、旧身份代码和自动建会话路径；更新 README、API 说明、种子脚本及 V2.1 人工验收清单；执行数据库迁移、权限、并发、幂等、Agent 安全、Worker、前端路由和真实模型冒烟测试。 | 两个注册账号可以分别发布商品、浏览商品、明确发起协商、完成议价审批和交易意向确认，并可交换买卖模式；纯浏览不产生会话；旧入口不能绕过统一认证；所有自动化检查和人工验收通过。 |

推荐依赖主线：

```text
统一账号数据模型
  → 统一认证与资源权限
  → 前端路由和模式入口
  → 商品大厅与卖家公开页
  → 显式创建/恢复协商
  → 卖家工作台整合
  → 兼容清理与全量验收
```

阶段 1～2 先使用 API 和自动化测试证明数据与权限正确；阶段 3～6 再逐步替换前端。不能先删除旧认证，再留下尚未接入统一登录的业务接口。涉及会话创建的阶段必须测试双击、并发、重复请求和自我协商；涉及迁移的阶段必须同时测试现有库升级与空库安装。

每个阶段结束前必须执行：

1. 复核本阶段认证、资源所有权、公开字段和会话状态边界；
2. 运行相关 Pytest 单元与 MySQL 集成测试；
3. 运行 Ruff、Alembic 当前版本和迁移一致性检查；
4. 运行前端类型检查和生产构建；
5. 检查差异中是否包含真实密钥、密码、Cookie、临时文件或无关修改；
6. 修复自检问题并重新验证后，才能标记阶段完成。

## 八、V2.1 最终验收

至少使用两个注册账号 A、B 完成以下流程：

1. A 注册并登录，不选择买家或卖家身份。
2. A 进入卖家模式，发布并上架商品。
3. A 切换买家模式，只能浏览自己的商品，不能对其发起协商。
4. B 注册并登录，浏览商品大厅、A 的公开卖家页和商品详情；此时数据库会话数量不变化，A 的卖家协商列表也没有新记录。
5. B 点击“与卖家协商”，创建会话并进入协商页；A 此时可以看到该协商记录。
6. B 重复点击或刷新协商入口，只恢复同一个进行中会话。
7. A 与 B 完成一轮包含正式报价、必要时卖家审批、Worker 通知和买家确认的完整 V2 闭环。
8. A、B 均可在不重新注册或登录的情况下切换买卖模式，但只能操作归属于自己的资源。
9. 第三个账号不能读取 A、B 的私有商品策略、买家会话、审批详情或卖家管理数据。

V2.1 完成后，系统仍以“记录交易意向”为终点，不代表付款、库存锁定、订单创建或实际成交。

## 九、不属于 V2.1 的范围

- 固定买家/卖家角色和角色申请审核；
- 企业商户认证、店铺装修、关注、评价和客服团队；
- 购物车、收藏、搜索推荐和复杂商品分类；
- 支付、订单履约、物流、退款和真实库存锁定；
- 同一商品的跨买家竞价、独占预订和订单并发决策；
- 管理员后台、风控审核和社交登录；
- SSE、WebSocket 或移动端应用。

这些能力如需实现，应在 V2.1 的统一账号和资源权限基础上另行规划，不能扩大本次升级的验收边界。
