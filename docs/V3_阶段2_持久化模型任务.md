# V3 阶段二：持久化模型任务与执行状态

> 状态：已完成。阶段二只建立持久化任务、租约和状态转换基础，不改变现有聊天 API 与审批 Worker 的同步执行方式。真实模型调用迁移、结果二次复核和前端处理中状态属于阶段三。

## 一、目标与边界

阶段二为两类外部模型调用建立统一记录：

- `CHAT_DECISION`：买家消息对应的协商决策；
- `APPROVAL_FOLLOWUP`：卖家审批后生成的买家通知。

本阶段完成以下能力：

1. 同一 `task_type + business_key` 在数据库中只能存在一条任务，重复请求返回同一记录，不创建第二个执行事实；
2. 创建任务时从数据库捕获会话版本、不可变报价 ID 和策略版本，并保存规范化 JSON 输入及 SHA-256 哈希；
3. Worker 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 领取任务，获得唯一租约令牌和到期时间；
4. 任务可以进入成功、等待重试、终止失败或版本失效状态，过期租约可以被其他 Worker 接管；
5. 保存提供商、模型、Token 和估算成本，但模型输出只作为候选结果，不能直接成为报价、审批、消息或交易意向。

阶段二不实现指数退避公式、最大重试次数或人工恢复入口。`defer_retry` 只接受调用方显式给出的下次重试时间；统一退避和最终人工处理属于阶段四。

## 二、数据库模型

Alembic 迁移 `20260928_0007_v3_model_execution_tasks.py` 新增 `model_execution_tasks`。主要字段如下：

| 类别 | 字段 | 约束与用途 |
|---|---|---|
| 业务身份 | `task_type`、`business_key` | 组合唯一；分别区分聊天决策和审批通知。 |
| 业务引用 | `session_id`、`offer_id`、`approval_id` | 会话必填；询价型聊天允许没有报价；审批通知必须由 Service 校验审批与报价属于同一会话。 |
| 输入版本 | `snapshot_schema_version`、`session_version`、`policy_version` | 均为正数；报价本身不可变，因此以 `offer_id` 作为报价快照身份。 |
| 不可变输入 | `input_snapshot`、`input_snapshot_hash` | 输入先进行稳定 JSON 编码和深拷贝，再保存 64 位 SHA-256；相同业务键复用不同输入会被拒绝。 |
| 执行状态 | `status`、`attempt_count`、`next_retry_at` | 状态机和重试调度基础；等待重试时必须有 `next_retry_at`。 |
| 租约 | `lease_owner`、`lease_token`、`lease_expires_at` | 仅 `RUNNING` 状态允许存在；令牌全表唯一。 |
| 错误 | `last_error_category`、`last_error_message` | 错误使用稳定分类；消息只保存调用方提供的简短脱敏摘要，不保存堆栈、密钥或完整请求。 |
| 用量 | `model_provider`、`model_name`、Token 字段、`estimated_cost` | 成功完成时写入；未知用量保持 `NULL`，不按零处理。 |
| 候选结果 | `result_snapshot` | 可追溯的模型候选输出，不具备任何业务授权效力。 |

`session_id` 删除时任务随会话清理；报价或审批单独删除时对应外键置空，输入快照仍保留当时的引用。应用层在创建审批通知任务时强制校验已审核状态及审批—报价—会话归属；任务保存创建时的当前策略版本，审批记录另行保留审核所依据的策略版本，阶段三据此判断审核在任务创建前或模型调用期间是否已经失效。

## 三、任务状态机

```text
PENDING ──领取──> RUNNING ──成功──> SUCCEEDED
                      │
                      ├──可重试失败──> RETRY_WAIT ──到期领取──> RUNNING
                      ├──永久失败────> FAILED
                      └──版本过期────> STALE

RUNNING ──租约到期后由其他 Worker 领取──> RUNNING（新令牌，尝试次数递增）
```

`CANCELLED` 为阶段三业务状态复核后的显式取消保留；阶段二没有提供可以绕过有效租约任意取消运行中任务的入口。

数据库检查约束保证：

- `RUNNING` 必须同时具有 owner、token 和 expires_at，其他状态不得残留租约；
- `RETRY_WAIT` 必须具有 `next_retry_at`，其他状态不得残留重试时间；
- 尝试次数、Token 和估算成本不能为负数；
- 输入哈希长度固定为 64。

## 四、Service 契约

`ModelTaskService` 不依赖模型 SDK，也不会修改消息、报价、审批或会话终态。

| 方法 | 行为 |
|---|---|
| `create_task` | 校验业务键和 JSON，锁定会话及策略并捕获版本，校验报价/审批归属，按唯一键幂等创建。 |
| `get_task` | 返回深拷贝快照，调用方修改返回值不会改变 ORM 实体。 |
| `lease_next` | 领取 `PENDING`、已到期 `RETRY_WAIT` 或租约已过期的 `RUNNING` 任务；并发 Worker 通过跳锁避免重复领取。 |
| `complete_success` | 只有未过期且令牌匹配的租约可以保存候选结果和模型用量并进入 `SUCCEEDED`。 |
| `defer_retry` | 保存错误分类和未来重试时间，清除租约并进入 `RETRY_WAIT`。 |
| `fail_task` | 由有效租约将不可重试错误写入 `FAILED`。 |
| `mark_stale` | 由有效租约把版本或业务事实冲突写入 `STALE`，阻止迟到结果继续处理。 |

所有完成方法都检查状态、租约令牌和过期时间。旧 Worker 即使在租约过期后返回，也不能覆盖新 Worker 的任务状态。

## 五、幂等与不可变性

业务幂等键不是数据库自增 ID 的替代显示值，而是由上层业务事实稳定生成：

- 聊天决策建议使用 `chat:{session_id}:{buyer_request_id}`；
- 审批通知建议使用现有 `followup_request_id` 或其带任务类型前缀的等价值。

相同类型和业务键再次创建时，只有会话、报价、审批、快照版本及输入哈希全部一致才返回 `idempotent_replay=True`。任一字段不同都会产生业务冲突，不能静默覆盖旧输入。

输入 JSON 在写入前按键排序、禁止 `NaN/Infinity`、进行深拷贝并计算哈希。数据库记录创建后，Service 不提供修改输入、业务引用或版本字段的方法。后续阶段如需升级输入结构，必须提升 `snapshot_schema_version`，不能原地改写旧任务。

## 六、安全边界

- `result_snapshot` 是模型候选结果，不是可执行命令。阶段三只有在重新锁定并校验会话、商品、报价、审批、策略版本和幂等键后，才能把确定性结果写入业务表。
- 任务表不保存 API Key、认证 Cookie、数据库连接串或模型内部推理；错误消息必须先脱敏并限制为 500 字符。
- 输入可能包含业务上下文，只允许保存在业务数据库中，不应原样写入普通日志或公开 Trace；阶段六会继续定义字段级脱敏和留存策略。
- 阶段二没有把现有长事务模型调用迁移到新任务表，因此不能据此宣称数据库锁等待问题已经解决。

## 八、阶段三入口

阶段三应在本阶段 Service 之上实现以下三段式流程：

1. 短事务写入买家消息或读取已审核审批，创建任务并提交不可变输入；
2. Worker 领取任务后在事务外调用模型，不持有会话、报价、审批或策略行锁；
3. 新事务使用租约令牌重新锁定业务事实，对比任务中的会话、报价和策略版本，再幂等写入消息、报价或安全终态。

阶段三不能直接把 `SUCCEEDED.result_snapshot` 复制到消息表。复核失败必须进入 `STALE` 或明确取消状态；重复完成、旧租约和过期输入必须保持无业务写入。
