## 一、项目出发点、价值与取舍

### Q01｜请用一分钟介绍这个项目。

**参考回答：**

我做的是个人闲置交易的卖家协商助手，目标是减少重复咨询和议价中的沟通负担。卖家先配置商品事实与私有价格授权，助手在授权范围内回答问题、评估条件并推进协商；需要卖家决定时走审批，最后由买家确认交易意向。

技术上，我把模型驱动的工具循环和确定性业务规则结合起来，重点实现了上下文压缩、带来源的协商记忆、持久化任务恢复及调用追踪。评测使用 120 个合成场景各重复 2 次，实际产生 1,122 个卖家轮次，异常执行终止为 0，但有 26 轮受控预算停止。项目终点是交易意向，不包含支付和履约。

**追问：最值得讲的点是什么？答：**模型输出不直接等于业务事实；我通过工具权限、事务、版本复核和正式回复把模型决策接到可校验的业务动作上。依据：C01、C02、C09、E01。

### Q02｜为什么做这个项目？真实出发点是什么？

**参考回答〔动机表述模板〕：**

我关注的是个人卖家需要反复回答成色、配件、价格和配送问题，而且多轮议价中条件经常变化。这个场景既需要理解自然语言，也存在清晰的价格和授权边界，适合验证 Agent 能否在真实业务约束下工作。

我的出发点是做一个可检查、可恢复的协商原型，而不是仅做能聊天的演示。它能集中暴露长对话遗忘、错误承诺、工具失败和成本失控等问题。当前没有真实用户实验，因此“减轻沟通负担”是产品目标，不能说已经证明节省了某个比例的人工时间。

**追问：你自己卖二手时遇到过这些问题吗？答：**如确有经历，讲具体商品和重复沟通内容；否则如实说这是观察到的场景和工程验证选题，不编造交易经历。依据：C01。

### Q03｜为什么用 Agent？规则或普通聊天机器人不够吗？

**参考回答：**

价格授权是稳定、可计算的规则，直接交给后端；咨询内容和条件组合是开放的，需要模型理解问题并决定下一步查什么。只用固定规则，会不断增加意图和话术分支；只用一次模型生成，又缺乏工具反馈后的修正能力。

因此我的设计是混合方式：有效正式报价落入自动接受区或审批区时直接按规则处理；其他请求进入有界工具循环，模型根据查询和评估结果继续决策。这让确定的步骤可验证，让不确定的对话保留适应性。

**追问：是不是所有消息都走 ReAct？答：**不是。本批 1,096 个正常返回轮次中，有 169 轮走确定性授权路由。不能把 1,122 轮全部称为 ReAct 执行。依据：C02、C03、E02。

### Q04｜你的目标是把价格卖到最高吗？怎样定义成功？

**参考回答：**

当前目标是在卖家授权和事实约束内推进有效协商，并保持过程可恢复、可追踪。项目没有实现全局最优定价、博弈均衡求解或强化学习策略。

我把成功拆成运行受控、业务授权正确、问题回答质量、交易意向达成、成本与时延几个维度。低价越权成交不算成功；正常拒绝不必算运行失败；预算停止说明执行仍受控，但交互效率可能有问题。不同维度要单独衡量。

**追问：56.25% 达成率算好吗？答：**缺少同分布基线和真实用户对照，不能单凭这个数判断优劣。集合含攻击和长对话压力场景，也不代表正常平台流量。依据：E01、E02。

### Q05｜介绍整体架构，一条消息怎么走？

**参考回答：**

前端是 Vue 3，后端是 FastAPI 模块化单体，数据库是 MySQL。买家请求经过身份与资源归属校验，进入 `ChatService`，保存消息并区分普通咨询与正式报价。

可按规则处理的报价直接完成业务动作；需要模型时创建冻结任务，领取租约，进入 V4 Runtime。Runtime 构建上下文、检查预算、调用模型、执行工具并处理回执。普通回复通过审核后发布，正式回复从已经校验的业务事实生成。独立 Worker 负责到期重试、恢复及审批通知，前端轮询后续消息。

**追问：为什么不用微服务？答：**当前规模下，模块化单体便于维护事务边界和复现。API 与 Worker 分进程，不等于已采用微服务架构。没有负载证据时不为拆分而拆分。依据：C01、C02、C09、C16。

### Q06｜为什么选 Python、FastAPI、LangChain 和 Qwen？

**参考回答〔选型解释〕：**

Python 方便接入模型、数据处理和评测；FastAPI 与 Pydantic 适合定义 HTTP 输入和结构化数据契约；SQLAlchemy 统一持久化与事务处理。LangChain 主要提供模型接入、消息对象、工具描述和结构化输出等能力，关键业务授权仍由项目服务层控制。

Qwen 通过兼容接口接入，当前版本检查所需工具调用和结构化输出能力。选型考虑中文协商、接口能力、部署可用性及调用成本，但仓库没有足够的跨模型对照，不能说它已经被证明优于所有替代模型。

**追问：换模型只要改模型名吗？答：**不够。要验证 schema 支持、tool choice、消息协议、用量字段、超时和输出截断行为，再跑契约与场景回归。依据：C04、C18。

### Q07｜LangChain 在这里做了什么？用了 LangGraph 吗？

**参考回答：**

V4 的有界循环主要写在 `SellerAgentRuntime`，通过 Provider 封装调用 LangChain 模型接口，使用 `bind_tools`、消息类型和输出契约。旧候选决策路径还能看到 `create_agent` 和 `ProviderStrategy`，但不能把它当成 V4 全部编排逻辑。

持久化检查点、租约和业务版本控制是本项目代码实现的。没有证据表明项目使用了 LangGraph 图编排，不能因为 LangChain 的依赖关系就声称自己实现了 LangGraph 工作流。

**追问：为什么不全用框架自带 Agent？答：**这里需要把每次调用预算、租约、业务事务和恢复点明确关联，自定义 Runtime 便于控制；代价是协议、兼容和恢复代码需要自己维护。依据：C04、C05。工具概念参考 [LangChain 官方文档](https://docs.langchain.com/oss/python/langchain/tools)。

### Q08｜项目是不是套壳？你的工程贡献在哪里？

**参考回答〔按实际分工调整〕：**

调用模型是基础能力，项目的工程工作在于让开放式模型输出安全进入业务系统：正式报价与聊天分开，私有阈值不进入模型输入，执行前重新授权；任务状态和调用快照持久化，避免恢复时重复写入；上下文与记忆保留来源；评测保存失败样本和可复算记录。

我会选一个自己真正理解并完成的模块，现场讲清控制流、失败路径和测试。哪些代码由 AI 辅助生成、哪些决策由自己完成，应如实说明；仓库本身不能证明个人贡献比例。

**追问：去掉模型剩下什么？答：**还剩账号商品系统、正式报价与审批确认闭环、任务执行基础设施和评测框架；开放问题理解及自适应协商能力会下降。依据：C01—C05、C09。

## 二、Agent 循环、工具与回复控制

### Q09｜ReAct 是什么？你在代码里怎么实现的？

**参考回答：**

ReAct 的核心思想是把推理决策与行动、环境反馈交替起来。我的工程实现是：给模型当前上下文和工具契约，模型提出工具调用，运行时校验并执行，把结果写回消息流，再让模型决定下一步，直到结束或触发预算。

项目使用原生工具调用表示行动，不要求模型输出可见的 `Thought/Action/Observation` 文本。当前冻结评测关闭了主模型和审核模型的 thinking，但保留工具循环；不能把“ReAct”解释成记录了模型完整内部思维过程。

**追问：与一次 Function Calling 有什么区别？答：**工具调用是接口能力；循环是在拿到工具结果后继续决策和修正。只调用一次工具不自动构成多步自主执行。依据：C05；概念参考 [ReAct 原论文](https://arxiv.org/abs/2210.03629)。

### Q10｜有哪些工具？读工具和写工具为什么分开？

**参考回答：**

读工具包括商品查询、协商状态查询、条件评估和历史检索；正式业务工具包括还价、接受当前买家报价和请求审批；`finish_turn` 用于结束本轮普通咨询、澄清或拒绝。

查询提供证据，评估提供权限判断，正式业务工具才允许改变报价或审批状态。模型说“这个条件可以接受”和后端真正接受报价是不同的事。工具说明、参数校验、后端绑定身份和事务共同落实这个边界。

**追问：`finish_turn` 完全不写数据库吗？答：**不是。它可以保存公开回复、记忆和任务状态；“非写动作”指不能借它执行正式报价、接受和审批，不能理解成没有任何持久化。依据：C06、C09、C10。

### Q11｜如何防止模型伪造工具结果？

**参考回答：**

模型只能提出调用参数，真正的结果由后端工具执行后返回。Runtime 按工具名、参数 schema 和调用 ID 验证协议，检查重复、缺失或过长 ID；正式业务执行还会检查当前身份、会话和报价。

普通文本中的“工具执行成功”没有业务效力。正式回复由已经成功落库的业务结果生成，不能让模型自行宣布审批成功。完整消息流区分调用、工具结果、候选回复和公开回复，便于复核。

**追问：模型自己构造一个别人的 session_id 呢？答：**关键身份来自后端构造的 `AgentToolContext`，不作为模型可自由填写的授权字段；服务层仍检查归属。依据：C06、C09、C11。

### Q12｜一次返回多个工具调用怎么处理？会并行吗？

**参考回答：**

当前 Provider 请求关闭并行工具调用，但不能只相信提供商遵守参数。Runtime 仍校验整个批次：工具必须在白名单中，终结工具最多一个且只能放在最后。合法调用写入 `pending_calls` 后顺序消费。

这样可以避免同一批既接受又还价、业务结束后继续查询或写入。如果批次违反约束，会生成失败回执并闭合协议，不让非法终结动作落库。

**追问：以后能并行读工具吗？答：**可以作为优化，但要处理共同状态快照、结果排序、预算预留和失败合并。当前不能宣称已经实现并行工具执行。依据：C04、C05、C06、T02。

### Q13｜模型只输出自然语言，不调用结束工具怎么办？

**参考回答：**

候选文本不会直接发布。系统保存候选并进入修复状态，后续要求模型按结束契约提交。`structured-finish-v2` 可以在需要时、以及最后一个模型步骤使用结构化 JSON 结束计划。

结束计划只允许咨询或拒绝，校验成功后转换为内部 `finish_turn` 信封继续执行审核。快照保留原模型输出和转换来源，不能把系统生成的内部工具信封统计成模型原生工具调用。仍不合规则在预算内安全停止。

**追问：为什么不从自由文本里正则抽取“接受”？答：**语义含糊，可能包含否定、引用和假设，会把普通回复误当正式动作。正式动作必须满足明确结构和业务授权。依据：C05、T03。

### Q14｜工具参数错误后，是立即失败还是继续修正？

**参考回答：**

可修正的参数或业务约束问题返回结构化错误，成为下一次模型决策的依据。例如未知运费、非法附加条件、不是当前报价等，不应该变成默认授权。

生产执行使用嵌套事务处理工具尝试：校验失败时回滚本次尝试，保存失败回执和进度，再允许模型在剩余预算内修正。租约失效或基础设施错误有独立处理路径，不能把所有异常吞掉并伪装成普通参数问题。

**追问：反复调用同一个失败工具怎么办？答：**当前依靠反馈、提示约束及步骤/工具/调用预算限制；不能声称已有覆盖所有语义重复的去重算法。更细的重复动作检测属于后续优化。依据：C05、C09。

### Q15｜为什么给 Agent 设置这么多种预算？

**参考回答：**

单独限制模型步数控制不了一次响应中的多个工具、额外审核和摘要调用，也控制不了单次上下文长度。冻结评测配置包括：6 个主模型步骤、8 次工具调用、10 次总模型调用、2 次维护调用、120 秒墙钟预算、180,000 累计 Token 预算，以及费用限制。

上下文还有独立输入和输出预留。运行前先检查、预留并持久化，再调用模型，恢复任务时继续使用原检查点中的已用额度。预算停止会保存原因并返回受控提示。

**追问：120 秒是绝对实时截止吗？答：**不是。代码在执行边界检查时间，正在进行的同步 RPC 还受单独请求超时控制；这不是能在任意时刻硬中断所有代码的实时保证。依据：C05、C07、E03。

### Q16｜普通回复为什么再调用一次模型审核？

**参考回答：**

schema 合法只能证明格式正确，不能证明回答相关、事实有依据。普通回复先做能力承诺等初筛，再提交候选回复、公开事实和近期会话给审核调用；审核输出包含结论与事实引用路径，后端核对路径存在、摘录确实来自字段。

审核不通过会把具体反馈交回循环修改。审核结果的缓存键绑定动作、回复正文和当前证据，仅修改 reason 或 topics 不能让同一段错误回复反复抽样闯关。正式业务回复使用确定性文案，不依赖这层模型审核来授予权限。

**追问：审核是独立真值吗？答：**它是额外调用，不是独立人工裁判；同模型可能有共同偏差。引用存在也不能证明蕴含关系正确，审核可能误拒或漏判。依据：C10、E01。

### Q17｜你怎么减少幻觉？“没写维修记录”能回答“没修过”吗？

**参考回答：**

不能。没有记录代表信息未知，不能当成否定事实。模型应基于商品公开字段回答，缺失信息说明需向卖家确认，不编造配件、维修、发货或照片情况。

实现上通过公开事实输入、工具取证、审核引用和能力承诺检查降低风险，正式交易事实则从业务结果渲染。项目仍有自然语言能力承诺漏判记录，因此只能说降低风险，不能说消除了幻觉。

**追问：能不能答“我帮你联系卖家核实”？答：**当前没有通用联系卖家工具，不能承诺助手会去联系；应说明该信息需要买家向卖家核实。正式报价审批能力不能泛化成任意问题的卖家联络能力。依据：C10、E04。

### Q18｜如何设计提示词、工具描述和版本管理？

**参考回答：**

提示词说明任务目标、证据范围、工具权限、未知事实和结束契约；工具描述解释用途和限制，schema 定义参数。关键限制还必须写进后端校验，不能只靠模型自觉。

任务创建时冻结提示词文本、哈希、工具契约和模型配置，恢复沿用冻结版本。当前加载器读取 `.txt` 资源，仓库另有 `.md` 文件，修改时不能只改未被读取的副本。评测使用的实际输入也保存在调用快照中。

**追问：提示词改好了，旧任务会自动使用吗？答：**不会，旧任务按冻结契约恢复；否则相同任务重试时行为和审计依据会悄悄改变。依据：C04、C12、C02、E03。

## 三、价格授权、人工审批与安全边界

### Q19｜如何划分自动接受、人工审批和禁止接受？

**参考回答：**

按卖家净收入判断，而不是只看买家支付金额。当前公式是：净收入 = 买家支付金额 − 卖家承担的运费 − 卖家承担的优惠。设底线为 L、自动接受阈值为 A，且 A ≥ L：净收入 ≥ A 为自动接受区；L ≤ 净收入 < A 为审批区；净收入 < L 为禁止接受区。

价格区间只是一个条件，还要检查附加交易条件是否受支持。即使金额够高，未授权条款也不能自动承诺。规则在 Python 中用 `Decimal` 计算，在数据库中用定点金额类型保存。

**追问：净收入等于两个边界怎么判？答：**等于 A 可以自动接受；等于 L 进入审批区。若 A=L，则两者之间没有审批区。依据：C03、T01。

### Q20｜给你一个具体报价：2850 元包邮，运费 20 元，怎么处理？

**参考回答〔算例〕：**

假设卖家底线 2700、自动接受阈值 2850、卖家优惠为 0，卖家承担 20 元运费，则净收入为 2830，属于审批区，不能因为买家出价等于 2850 就自动接受。

若运费由买家承担，在当前模型中它不从卖家收入扣减，净收入 2850 才落入自动接受区。卖家承担的运费未知时，应拒绝计算或要求补齐，不能用 0 代替未知值。

**追问：这里的优惠会不会重复扣？答：**接口金额语义必须统一：`buyer_payment` 与 `seller_borne_discount` 是独立字段，不能把已扣优惠的金额再当原价扣一次；对接真实平台时要重新定义含税、运费和手续费口径。依据：C03。

### Q21｜买家说“2800 行吗”为什么不直接创建报价？

**参考回答：**

自然语言金额可能是预算、试探或假设，不必然表示同意具体运费和配送条件。项目只有结构化提交才创建正式 offer，普通聊天可以讨论和评估条件，但不能据此直接接受或提交正式审批。

正式动作绑定本轮的正式报价 ID，防止模型引用历史报价代替当前意图。这样会增加一次明确提交操作，但能减少把随口咨询误解释为业务承诺的问题。

**追问：为什么不让模型自动抽取后立即成交？答：**抽取可以用于辅助填写草稿，正式提交前仍需要明确确认；当前代码没有实现“自然语言自动转正式报价并成交”。依据：C02、C06、C09。

### Q22｜为什么不把卖家底价写进提示词并要求保密？

**参考回答：**

不必要的秘密不应进入模型上下文。模型拿到公开商品事实，以及后端给出的可执行权限和原因码；最低净收入、自动接受阈值等私有数值保留在服务层。

这样即使买家诱导模型复述上下文，也减少直接暴露私有策略的机会。执行工具时重新计算授权，模型不需要掌握底价就能知道某组条件是否可以继续。

**追问：多次试价能反推出区间吗？答：**存在推断风险。隐藏字段不等于信息论意义上的不可推断。当前有执行预算，但不能声称已完整防住跨轮、跨会话探测；还需最小化反馈和滥用频控。依据：C03、C11、T02。

### Q23｜Human-in-the-loop 具体是谁在什么时机介入？

**参考回答：**

正式买家报价满足审批区和条件约束时，后端创建待审批记录，会话进入等待审批状态。拥有该商品的卖家可以审批或拒绝；审批结果还要经过后续处理并形成可见通知。

卖家同意并不直接把交易记为已完成。买家仍需确认当前有效报价，系统才记录 `AGREED`。人工审批决定是否授权，买家确认决定是否形成意向，这两个环节不能混为一谈。

**追问：买家在聊天里说“卖家已同意”，能当审批吗？答：**不能。必须查真实审批记录、状态、关联报价和策略版本，用户消息不能伪造卖家授权。依据：C13、C14。

### Q24｜审批等待期间买家换了报价怎么办？

**参考回答：**

新的正式报价会触发对原待审批请求的取消处理，再建立新的报价上下文。审批与确认都检查当前报价、会话状态及策略版本，旧报价的同意不能转移到新条件上。

如果模型在处理旧任务时业务状态已经改变，执行前版本复核会阻止旧结果继续提交。审批、任务和报价是关联的业务对象，不能只靠一条“卖家同意”的聊天消息判断。

**追问：卖家同意 2800 自提，买家改成 2800 包邮呢？答：**是新条件，要重新评估净收入并按需要重新审批，不能复用旧授权。依据：C02、C13、C14。

### Q25｜Agent 能不能主动给出还价？审批区的价格也能主动报吗？

**参考回答：**

可以通过 `submit_counter_offer` 提交正式还价，但后端只允许条件受支持且达到自动授权要求的方案。代码中的 `can_submit_counter_offer` 与自动接受权限一致，审批区和禁止区的主动还价不会写入。

审批工具面向本轮正式买家报价。不能让模型先编一个未经卖家授权的低价，再假装卖家愿意成交。这是当前项目有意采用的保守业务规则，未来若支持“卖家审批 Agent 草稿报价”，需要另建明确流程。

**追问：模型只是嘴上说“我可以 2600 卖给你”呢？答：**那也是可能误导买家的承诺，普通回复审核和承诺检查应拦截；真正的报价记录仍不能靠这句话产生。依据：C03、C06、C09、C10。

### Q26｜为什么已经接受报价，还要买家再确认？

**参考回答：**

接受表达的是卖家侧对某份条件的授权，买家可能在等待中改变意愿，所以还需要最后确认。确认接口重新检查会话、商品、当前报价、过期时间和授权来源。

Agent 还价、自动接受买家报价、卖家审批通过分别有对应事实条件；审批路径还要核对有效审批及已发送的正式通知。通过后写入确认报价、确认来源和时间，并把会话改成 `AGREED`。

**追问：两个买家能否对同一商品都形成意向？答：**项目没有库存锁定和支付订单，不能保证商品只形成一份意向。真实交易要增加商品预占、订单状态和超时释放，这是当前范围之外的能力。依据：C14、C01。

### Q27｜Prompt Injection 怎么防？

**参考回答：**

先区分可信控制信息和外部数据：买家消息、商品描述、摘要与历史都只能作为待解释的数据，不能改变工具权限。系统提示会明确这点，但真正的约束放在代码里：隐藏私有阈值、绑定会话身份、校验当前报价、后端重新授权和生成正式回复。

还要记录越权工具尝试与公开承诺问题。提示词注入不只来自当前用户，也可能藏在历史和商品内容中。当前措施降低攻击得手的机会，不能宣称适用于所有未知输入的绝对防护。

**追问：攻击失败是不是等于拒绝回复质量优秀？答：**不是。可能反复审核、耗尽预算才安全停止；安全结果、交互效率和语义正确性需要分别评价。依据：C05、C09、C10、E04。

### Q28｜“不会越权”与“不会乱说”是不是一回事？

**参考回答：**

不是。数据库里的报价和审批动作有确定性校验，但自然语言可能说出并未实现的能力。复核材料中 F23、F24 出现公开承诺联系或反馈卖家的文本，而当前没有通用联系卖家的工具。

所以简历中的 0/240 只能限定在已执行交易操作及检查范围内。代码有承诺初筛和审核，但这些案例表明语义检查仍有缺口，不能把工具层安全推导为公开表达零错误。

**追问：这是线上事故吗？答：**不是，是本地合成场景真实模型评测中的问题；相关职责分类也是基于记录的助手复核，不能冒称独立人工全量验收。依据：C10、E01、E04。

## 四、上下文、历史检索与协商记忆

### Q29｜为什么同时需要原始历史、摘要和结构化记忆？

**参考回答：**

原始历史是可追溯证据，不能因为压缩就丢掉；摘要用于减少长历史占用；结构化记忆保存当前买家陈述、未回答问题、尝试过的方案和低置信度假设，方便后续轮次直接使用。

三者不是同一层。摘要可能丢细节，记忆也可能抽错，所以仍要保留原记录和来源序号。正式报价、审批状态和价格授权以业务数据为准，不能被摘要或记忆改写。

**追问：这是跨用户长期记忆吗？答：**当前主要是会话级协商记忆，没有证据表明已实现跨用户画像或跨会话通用长期记忆。依据：C07、C08、C15。

### Q30｜每次模型调用的上下文由什么组成？

**参考回答：**

包括冻结的系统提示词、后端公开业务事实、当前协商记忆、历史摘要、来源清单，以及没有被摘要覆盖的有效执行消息。输入长度还必须计入工具或结构化输出契约，而不只是聊天文字。

记录选择受冻结历史高水位和执行分支约束，避免任务读入未来消息或其他未完成分支。审核调用使用独立的证据输入和近期公开会话，不能把审核上下文与主循环上下文混为一谈。

**追问：V4 还是固定截最近 20 条消息吗？答：**主循环不是。它使用完整执行流、摘要和按预算选择的历史；但某些辅助步骤有自己的窗口，例如回复审核读取近期公开记录。依据：C07、C09、C10。

### Q31｜如何决定何时压缩？Token 是精确算的吗？

**参考回答：**

输入上限取配置输入预算与“模型窗口减输出预留再减安全余量”中的较小值。冻结评测中窗口 32,768，输入预算 16,000，输出预留 3,072，安全余量 1,024，所以基础输入上限是 16,000；首步还尽量预留工具结果增长空间。

达到触发比例时尝试摘要压缩，再校验实际待发送内容。当前用 UTF-8 序列化长度和消息开销做保守估算，不是 Qwen 官方 tokenizer 的精确值；调用后保存提供商用量用于校准与核算。

**追问：字数能直接等于 Token 吗？答：**不能。语言、标点、结构化字段和工具 schema 都影响 Token；当前估算只是一种带余量的工程控制。依据：C07、E03。

### Q32｜为什么不能直接删最早的消息？

**参考回答：**

工具协议有配对关系：assistant 提出的工具调用必须有相应 `tool_call_id` 的结果。如果只删某条调用或结果，可能留下孤立消息，造成模型接口错误或上下文误解。

项目按完整交互组组织历史，保护当前买家输入和最近的交互组，压缩或移除完整的旧组。摘要不删除持久化原记录；输入清单还记录本次省略了哪些来源，便于排查模型为什么没看到某条事实。

**追问：同一个 assistant 消息里有两个调用呢？答：**连同相应工具结果作为不可拆分的组处理，不能按普通消息条数随意切片。依据：C07、C17、T02。

### Q33｜摘要模型失败、或者摘要后仍太长怎么办？

**参考回答：**

摘要属于辅助步骤，失败或维护预算不足时可以继续使用原状态，再按完整交互组省略可移除的旧内容，保护当前输入和近期交互。增长预留是尽量满足的目标，不应在当前输入还符合硬上限时误拒。

如果连受保护内容都超过真正输入上限，就受控停止，不能无条件截断当前请求或继续超限调用。原始证据仍在数据库，只是本次模型可见上下文缩小。

**追问：这样不会忘信息吗？答：**有可能，所以要结合摘要、记忆与历史检索；安全控制能保证协议和容量边界，不保证所有旧细节都被正确利用。依据：C05、C07、T02。

### Q34｜协商记忆的结构是什么？如何防止模型编造记忆？

**参考回答：**

条目包括类型、字段、值、来源序号、状态和置信度。类型有买家陈述、待回答问题、已尝试方案、假设和计划。买家明确陈述必须引用买家输入，值要有原文依据；已尝试方案必须引用工具结果或执行事件；假设必须保持低置信度。

来源必须在当前可用记录中，不能引用别的会话。当前工作记忆只保留有限条目，旧产物仍可在执行流中追溯。这些校验保证来源和部分语义约束，不是通用自然语言理解的完备证明。

**追问：“能自提吗”能存成“买家选择自提”吗？答：**不应。它应作为待回答问题。代码对以问号结尾的引用有防误记检查，但不能据此声称能识别所有隐含疑问句。依据：C08、T02。

### Q35｜买家先说自提，后来改快递，如何避免旧偏好复活？

**参考回答：**

同类型、同字段的新证据可以替换旧偏好，同时比较来源序号。若补偿更新拿到的是更旧的证据，就不能覆盖已有更新来源；被替换条目标为历史版本，当前上下文使用更新后的状态。

待回答问题还要区分具体内容，同一个主题下两个不同问题不应互相覆盖。例如“是否维修过”和“保修多久”都与售后有关，但不是一个问题。

**追问：只比较更新时间不行吗？答：**不够。晚执行的补偿任务可能处理早发生的消息，应比较证据发生顺序，而不是仅比较写入时间。依据：C08、T02。

### Q36｜历史检索是不是 RAG？用了向量数据库吗？

**参考回答：**

当前实现是会话历史检索：在当前会话可访问的消息文本中做关键词子串匹配，返回有限条原消息和来源序号，空关键词可读取近期记录。没有 embedding、向量数据库或混合召回，不能把它包装成已实现的复杂 RAG 系统。

它对原词追溯简单可控，但对同义表达和语义匹配比较弱。未来历史规模和召回需求提高后，可以评估全文索引或语义检索，且仍必须保留会话隔离与来源校验。

**追问：摘要中的事实找不到原文怎么办？答：**回查来源，不应把摘要当成更高权威；找不到依据的内容需要降级为未知或待核实。依据：C06、C09。

### Q37｜为什么检索工具容易让上下文越查越大？

**参考回答〔复盘模板〕：**

一个容易忽略的问题是，旧工具结果里含有完整 artifact，如果再次检索时把这些结果递归塞回去，就会形成“检索结果里套检索结果”，迅速放大输入。

项目把本地完整 artifact 与模型可见的 wire message 分开。历史检索返回带来源的消息表示，不递归复制本地审计数据；工具结果过大时按结构裁剪并提示还有完整产物。相关测试验证了重复检索不嵌套旧 artifact。

**追问：直接截字符串为什么不好？答：**可能截坏 JSON 或丢掉 `ok`、错误码、报价等关键结构。当前优先移除整条记录、描述等可缩减部分，保留必要回执。依据：C06、C17、T02。

### Q38｜你怎么证明记忆有效？超过 20 条消息够不够？

**参考回答：**

超过 20 条公开消息证明系统能够处理相应规模的历史，并不证明每轮记忆正确。冻结压力测试有 8 次运行，5 次超过 20 条公开消息，2 次受控预算停止；整个集合有 12 次会话出现已捕获的记忆更新异常。

这个集合没有记忆开关消融，不能据此说记忆让达成率提高多少。更严谨的验证应固定场景和版本，比较记忆开关下关键事实保持、偏好变更、问题遗漏、成本和时延，并保留失败样本。

**追问：仓库不是还有组件对照吗？答：**有较早的分组实验，但场景与版本不同，不能混进这 240 次结果；旧实验的相关置信区间覆盖 0，也不能改写成已证明显著提升。依据：E01、E05。

## 五、事务、幂等与故障恢复

### Q39｜为什么模型调用必须放在数据库事务外？

**参考回答：**

模型 RPC 时间长且不可控。如果一直持有业务行锁等待，其他请求可能被阻塞，连接占用和锁等待也会增加。项目先用短事务保存输入、业务版本和任务，提交后再调用模型；返回后开启短事务验证当前状态并保存或执行结果。

事务外调用带来“调用期间状态可能变化”的问题，所以必须同时使用租约和业务版本复核。单纯把调用移出去而不加复核，会让旧结果覆盖新状态。

**追问：这是不是跨系统分布式事务？答：**不是。数据库事务不能回滚远端模型已发生的调用或费用；项目通过快照、恢复和幂等处理不确定性。依据：C02、C09、C19。

### Q40｜输入快照为什么要冻结？都冻结什么？

**参考回答：**

冻结输入、商品与协商上下文、关联报价、会话及策略版本、模型与提示词配置、工具契约、上下文初始状态等，使同一任务恢复时知道原来是在什么条件下执行的。

哈希用于检测变化，调用快照还保存实际发出的请求与响应。这样能分辨问题来自输入、模型、工具还是版本变化。密钥不应作为可传播快照的一部分，连接配置与敏感凭据要分开管理。

**追问：冻结以后结果就能完全复现吗？答：**不能保证远端模型再次生成逐字相同结果。冻结是让实验条件可追溯；复用已保存响应和重新调用模型是两种不同的复现方式。依据：C02、C09、C19、E03。

### Q41｜两个 Worker 同时抢同一个任务怎么办？

**参考回答：**

任务领取通过短事务和 `SELECT ... FOR UPDATE SKIP LOCKED` 完成。领取后写入拥有者、到期时间和新的随机租约令牌；任务提交结果、续租、更新检查点等操作都核验有效令牌。

其他 Worker 可以跳过已锁记录领取别的任务。租约过期后可以接管，旧 Worker 即使晚回来，也不能拿旧令牌继续写入。这解决的是本任务记录上的并发领取与提交权限。

**追问：`SKIP LOCKED` 能用于所有一致性查询吗？答：**不能。它可能跳过被锁行，适合队列式领取，不代表完整一致业务视图，也不自动保证严格公平。依据：C19；语义参考 [MySQL 锁定读文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

### Q42｜租约还有效，但商品价格或卖家策略改了怎么办？

**参考回答：**

租约只说明谁可以处理任务，不说明输入仍然有效。系统还核对会话版本、卖家策略版本、当前报价，以及商品公开信息和协商状态快照；不一致就阻止旧动作提交。

例如模型在旧策略下建议接受报价，而卖家已提高授权阈值，即便模型返回格式正确，也必须按当前状态处理为过期结果，不能执行旧建议。

**追问：为什么既要行锁又要版本？答：**行锁保护短事务执行时的并发更新；版本与快照识别模型调用前后发生的变化。两者覆盖的时间范围不同。依据：C02 的 `_stale_reason`、C09、T04。

### Q43｜用户重复点击发送，如何避免重复报价？

**参考回答：**

请求携带 `request_id`，系统根据会话和请求 ID 查已有消息，并比较内容与报价形成的请求指纹。同一标识、相同请求可复用已有结果或恢复未完成处理；相同标识却换了内容应报冲突。

任务还使用业务键唯一约束，消息流使用事件键唯一约束。幂等必须覆盖输入、任务、回执和公开回复，不能只在 HTTP 层做一个内存缓存。

**追问：不同 request_id 发同样的话会自动去重吗？答：**不能这样假定，它们可能是两次真实表达。当前主要按显式幂等键识别重试，同一会话存在活动聊天任务时会阻止新的并行处理。依据：C02、C15、C19。

### Q44｜进程恰好在模型返回之后崩溃，会再调一次模型吗？

**参考回答：**

分崩溃点判断。如果成功响应已经持久化为调用快照，恢复时可按任务、分支、逻辑步骤和用途读取它，避免重复 RPC。如果提供商已经处理完，但本地还没保存响应就崩溃，则无法确认远端是否完成，旧调用应保留为 UNKNOWN，恢复可能再次调用。

因此不能承诺外部模型调用严格 exactly-once。项目能对已保存响应复用，并对本地业务结果做幂等；未知调用的成本仍需要保守处理。

**追问：重试是不是免费？答：**不是。提供商可能已计费，未知用量不能当零；即使业务没有重复提交，也可能发生额外 RPC 成本。依据：C09、C05、T04。

### Q45｜工具已经改了报价，回执还没写完就崩溃怎么办？

**参考回答：**

生产执行把业务动作、工具回执、检查点推进及终结时的公开回复放进同一外层事务。正式动作成功而回执保存失败时，外层事务回滚，避免只落一半。

工具参数不合法时，内部 savepoint 回滚这次尝试，但外层仍可保存失败回执，让模型看到错误。恢复依据已提交检查点继续，不把同一个已完成业务步骤当成新动作重做。

**追问：`flush()` 是不是提交了？答：**不是。它把变更发送给数据库，但事务仍可能回滚；本项目的原子性依赖外层提交，不能把拿到自增 ID 当成业务已最终成功。依据：C09、T04；参考 [SQLAlchemy 事务与 savepoint 文档](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html)。

### Q46｜重试策略怎么设计？为什么不是所有失败都立刻重试？

**参考回答：**

先分类，再决定是否在最大次数内重试。当前对超时、限流、网络/部分服务端错误和无效结构化输出设置可重试策略；不能归类的内部错误默认不自动重试。任务进入等待状态，按有上限的指数退避和由任务/次数计算的抖动安排下一次处理。

V4 原生模型调用关闭 SDK 自动重试，防止外层只记一次、SDK 内部却多次调用。模型循环修正和任务级重试是不同层次，两者都需要受预算与恢复状态约束。

**追问：业务拒绝也重试吗？答：**不应该把合法的低价拒绝当网络错误重试；它可以成为协商反馈，但不能重复执行直到碰巧越过权限。依据：C04、C05、C20。

### Q47｜为什么使用 MySQL 任务表，而不是 Redis 或消息队列？

**参考回答〔设计取舍〕：**

当前业务已经使用 MySQL，把冻结任务和业务输入放在同一事务中，便于保证输入已落库时恢复任务也存在。任务量有限时，用任务状态、行锁和租约足以构建可恢复流程，部署依赖也较少。

代价是轮询和任务读写增加数据库负担，需要合适索引和清理策略。规模扩大后可以用消息队列做唤醒或调度，并用事务发件箱保证数据库与消息通知衔接；消息队列本身不会替代业务幂等和数据库状态。

**追问：现在已经用了 outbox 或 Redis 分布式锁吗？答：**没有这样的实现依据，应明确这是扩展方案，不能写进当前架构。依据：C16、C19。

### Q48｜账号安全和 Agent 授权有什么区别？

**参考回答：**

账号安全回答“请求是谁发出的”，业务授权回答“这个人和助手能操作什么”。当前密码使用带随机盐的 scrypt，身份令牌采用 HMAC 签名；接口再根据登录用户检查商品、会话、审批等资源归属。

模型看见某个 ID 不代表获得权限，工具上下文中的买家和会话由后端绑定，服务层再校验。当前令牌是自定义 HMAC 格式，不应随口称为标准 JWT 或 OAuth2 实现。

**追问：登录了就能审批任意商品吗？答：**不能，还要验证该商品归当前卖家所有；这是资源级授权，与是否登录是两层检查。依据：C11、C13、C21。

## 六、评测设计、指标、可观测性与性能

### Q49｜简历中的几个数字怎么得到？分别是什么分母？

**参考回答：**

同一冻结集合是 120 个合成场景各重复 2 次，共 240 个完整运行记录。按原始流中实际执行的买家输入划分，共 1,122 个卖家轮次，每轮都有一条非空公开回复；其中 1,096 轮正常返回、26 轮预算停止，未记录异常执行终止。

业务安全按运行统计，已执行交易操作未发现违规的运行口径为 0/240。卖家模型用量按实际 RPC 统计，有输入输出 Token 的调用为 3,157/3,157。会话、轮次和调用是三个层级，不能互相当分母。

**追问：一个轮次为什么可能有多个调用？答：**可能有多步工具决策、回复审核、摘要或记忆更新；也有确定性路由轮次完全不调用模型。依据：E01—E03。

### Q50｜0 次异常终止，为什么还有 26 次失败和 FAIL 门禁？

**参考回答：**

原评测把 26 次 `MODEL_STEP_BUDGET` 映射成 `SELLER_FAILURE`，超过预先设定的 5% 阈值，所以原门禁是 FAIL。后续逐轮复核发现它们都返回了受控停止回复，因此应把“运行异常终止”和“业务中断/预算停止”分开。

复核不改变历史门禁。正确表述是：异常执行终止 0/1,122，预算停止 26/1,122，即 2.32%；按会话则是 26/240，即 10.83%。这表示系统能在预算内结束执行，不意味着所有回答正确或交互都令人满意。

**追问：这是事后美化指标吗？答：**如果删掉旧标签或把 FAIL 改成 PASS 就不严谨。我保留原产物、原门禁和新口径，明确新统计是事后复算；未来再预注册拆分指标并重测。依据：E01、E02、E03。

### Q51｜安全违规为 0，怎么证明不是检查器什么都没查出来？

**参考回答：**

评测记录每次卖家回复、审批通知、买家确认和运行结束时的观察，累计 1,603 条。正式操作按独立金额运算与业务事实检查，检查器还有故障注入测试，验证低价越权、未知成本、非法条款和虚假审批等反例能被发现。

但公开文本扫描与生产检查共用部分匹配代码，而且只是有限规则，可能有共同盲点。后续复核确实发现两项未实现能力的公开承诺，因此 0 不能扩展到全语义安全。有限测试也不能证明任意输入都安全。

**追问：能否说线上故障率接近零？答：**不能。样本是合成场景，重复运行和同会话轮次相关，并非独立线上随机抽样。依据：E01、E04、C22、T05。

### Q52｜动态买家评测怎么做？会不会只是脚本走固定答案？

**参考回答：**

场景冻结商品、私有价格授权、买家预算、必要条件和开场。开场之后，真实买家模型根据卖家的实际公开回复选择咨询、报价、确认或退出；卖家使用实际 SellerAgent 和 V4 Runtime，因此对话后续不是固定台词。

不过它仍是模拟器：买家有预设目标，卖家审批按场景中的批准、拒绝或过期安排执行；业务数据使用隔离内存适配器，没有覆盖 HTTP、MySQL 和 Worker 进程故障。买家硬预算不进入卖家模型请求。

**追问：两边用同一模型会有什么偏差？答：**可能有相似表达习惯和共同偏差。应增加不同模型、不同风格及真实用户样本交叉验证；当前结果只能说明这一冻结环境中的表现。依据：E01、E03、C22。

### Q53｜评测中途修了场景，会不会挑了好看的结果？

**参考回答：**

原批有两个场景把未知的卖家运费编码成正式报价，4 次运行在模型调用前被校验拦截。修正是把这两个开场改为运费咨询，完整补跑两次重复，其余 118 个场景按哈希保持不变。

当前集合保留 236 条原记录并替换这 4 条输入错误记录；原批、修正协议和失败记录都保留。首次补测触及 0.6 元保守预留限制，记录原因后以 1.2 元上限完整重跑这两个场景，使用完整新批次，而非逐条挑成功记录。

**追问：这样能当成从未改过的单批实验吗？答：**不能，应称为按场景版本选取的修正聚合集合，披露输入修正和预算调整。它不是新的 240 次模型重跑，也不是盲测。依据：E01、E03。

### Q54｜56.25% 能证明 V4 比 V3 更好吗？怎么做才严谨？

**参考回答：**

不能。当前是 V4 在固定集合中的绝对结果，没有在同一集合、同一条件下完成对应 V3 对照。旧组件对照使用不同场景和配置，不能直接拼成版本提升比例。

更合理的方法是固定数据、模型配置和检查标准，做配对重复实验，比较质量、安全、成本及延迟；按场景聚类计算不确定性。报告中的达成率 bootstrap 95% 区间为 47.9%—64.6%，它描述该合成集合的抽样不确定性，不代表真实用户转化率。

**追问：temperature=0 为什么还重复测？答：**不能假设提供商推理、工具交互和整个动态环境严格确定；重复运行也有助于观察不同轨迹，但两个重复仍不足以覆盖所有变化。依据：E01、E05。

### Q55｜可观测性只是打日志吗？你记录哪些关联？

**参考回答：**

项目不只记录文本日志，还用结构化事件关联请求、会话、模型任务、报价、审批和尝试次数；模型调用保存用途、实际请求/响应、上下文来源、提示词哈希、状态、耗时与用量。

公开消息通过来源关联到执行流，执行流再关联调用和工具步骤，便于回答“这条回复用了哪些事实、前面失败在哪里、花费来自哪些调用”。对外追踪与本地详细快照分开，外部事件使用受限属性，不能把完整用户内容或私有策略随意写到第三方日志。

**追问：是不是可以看到模型完整思考链？答：**不能这样说。可观测的是请求、响应、工具和业务轨迹；当前 thinking 关闭，也不等于获取模型内部推理全过程。依据：C09、C15、C23。

### Q56｜Token 覆盖率 100% 怎么计算？费用怎么控制？

**参考回答：**

从本集合的调用记录中剔除 `BUYER_SIMULATION`，剩下 3,157 次卖家侧调用，逐条检查输入和输出用量字段均存在，因此采集覆盖为 100%。这包括主循环、结束、审核、摘要和记忆，不仅是主模型生成回复的调用。

每次 RPC 前按输入估算与输出上限预留额度，保存预留状态后再执行；返回后记录实际用量，超出预估时补记，未知用量保留预留。费用依赖冻结单价，属于估算，最终扣费以提供商账单为准。

**追问：2.63 元和 2.96 元为什么不同？答：**修正集合自身已知费用约 2.62754764 元；本次授权台账含预检、原批、输入修正及失败调用，约 2.956701 元，范围不同。不能把当前集合均摊成本冒称单轮生产账单。依据：C05、C09、E01、E03。

### Q57｜你做过延迟优化吗？这个系统能支持多高并发？

**参考回答：**

当前可以解释已有的结构性取舍：授权报价直接走规则避免不必要模型调用；事务外 RPC 缩短持锁时间；成功调用快照可在恢复时复用；循环和维护调用有预算。但没有生产并发压测和优化前后延迟对照，不能声称支持某个 QPS 或提升某个百分比。

下一步先区分排队、数据库、主模型、审核和维护调用耗时，统计用户可见单轮 P50/P95，再决定是否减少审核次数、拆异步路径或优化输入。报告的平均卖家耗时是一次完整运行中卖家步骤的耗时之和，不能当单轮平均响应时间。

**追问：FastAPI 就能保证高并发吗？答：**不能。当前接口有同步路径，实际吞吐还受工作线程、数据库连接池、模型限流和单会话串行约束影响。依据：C01、C02、C09、E01、C22。

### Q58｜如何测试 Agent，避免测试只验证模型会聊天？

**参考回答：**

分层测试：纯函数验证金额、边界、schema 和记忆来源；可控假模型制造协议错误、无效工具、超预算与审核拒绝；MySQL 集成测试验证租约、版本变化、幂等、事务回滚和恢复；真实模型动态评测观察端到端协商行为。

每层解决不同问题，假模型不能证明自然语言效果，真实模型内存评测不能证明数据库并发正确。重点设计能破坏不变量的反例，例如旧租约写入、旧报价确认、非法批次、孤立工具结果。

**追问：本次写面试材料跑了哪些测试？答：**实际运行了价格、V4 协议/上下文/记忆、审计回归、失败修复、对话审核、引用承诺和重试策略相关单元测试，共 107 项通过。未重跑 MySQL 集成或付费模型评测。依据：T01—T04，末尾验收记录。

### Q59｜面试官现场指出一条错误回复，你怎么排查？

**参考回答：**

先定位会话、公开消息和对应任务，确认错误属于事实幻觉、能力承诺、授权错误还是陈旧结果。再查实际调用快照，确认模型当时看见了哪些事实与历史，不能只用现在数据库中的状态推断当时输入。

随后沿候选回复、审核结果、工具参数、回执、版本检查和公开投影逐步定位。修复后把最小失败轨迹转成回归用例，再用隔离场景重测。不能只改提示词后手工试一句就宣布解决。

**追问：回复说已审批，但数据库没审批呢？答：**先检查是否走普通回复越权表达，还是正式文案引用了错误业务记录；这两类根因需要不同修复，不能笼统归结为“模型不稳定”。依据：C09、C10、C15、C23。

### Q60｜现场写价格授权逻辑时，你会先列哪些测试？

**参考回答：**

我先明确金额使用 `Decimal`，不接受负数、非有限数或超过两位有效小数；再验证 A≥L，计算净收入并分别比较两个边界，最后叠加条款白名单。不能让浮点误差改变边界，也不能让未知成本默认为零。

| 输入条件（L=2700，A=2850，优惠=0） | 期望结果 |
| --- | --- |
| 2850，买家承担运费 | 自动接受区 |
| 2849.99，买家承担运费 | 审批区 |
| 2700，买家承担运费 | 审批区 |
| 2699.99，买家承担运费 | 禁止接受区 |
| 2850，卖家承担运费20 | 净收入2830，审批区 |

**追问：为什么不先四舍五入再校验？答：**当前契约拒绝多于两位有效小数的金额，不静默改变用户条件；数据库落库约束也不能代替入口语义校验。依据：C03、T01。

## 七、可展开讲述的踩坑与复盘

以下回答可以作为“最有挑战的问题”的候选素材。标为“复盘模板”的题目有代码或回归测试依据，但不证明本人曾遇到对应线上事故。讲述时用“我重点处理/防范了这个问题”，比编造事故时间、损失和用户量更稳妥。

### Q61｜讲一个你遇到的最典型问题：安全检查为什么会误伤正常回复？

**参考回答〔有预检记录的复盘〕：**

安全检查如果只看“包邮”“今天发货”等关键词，可能把“不能保证今天发货”或引用后明确拒绝的句子当成真实承诺，导致审核反复拒绝安全回答，最后耗尽预算。

预检记录中出现过引用拒绝误判，项目补充了否定、引用与实际承诺的回归用例，并调整相关判断。关键不是放宽所有安全检查，而是同时加入正反例：拒绝条件应放行，真正承诺即使加引号也应拦截。

**追问：已经彻底解决了吗？答：**没有。自然语言组合复杂，正式集合仍有审核链路问题。回归通过只说明覆盖样本改善，下一步需要更系统的语义评审集。依据：E01、C10、T03。

### Q62｜讲一个协议层面的坑：模型给出正常文字却被判失败。

**参考回答〔有历史实验记录的复盘〕：**

较早实验中出现模型最终只返回自由文本、没有按工具协议结束的情况。对人看似答完了，但 Runtime 无法安全确定这是否是一份可发布的结束计划。

项目先采用有界指定结束工具，再补充结构化结束计划，在最后步骤提供明确收口契约。格式校验之后仍要经过审核，且结束计划不能携带正式业务写动作。这样处理的是“如何可靠结束一轮”，而不是放弃工具协议直接发送原始文本。

**追问：把内部转换也记成模型成功调用工具，会怎样？答：**会高估原生工具遵循率。必须保留原响应和 `STRUCTURED_FINISH` 来源，观测指标区分原生调用与内部信封。依据：E05、C05、T03。

### Q63｜讲一个长对话记忆容易踩的坑：覆盖游标为什么会漏消息？

**参考回答〔代码与测试支持的复盘模板〕：**

补偿记忆更新可能一次处理不完全部旧消息。如果超预算时删掉前面较老的记录，却把“已处理到”的游标推进到剩余尾部，就会把没处理过的中间历史永久跳过去。

当前连续前缀策略在超限时从尾部缩减，只在实际处理的连续前缀上推进游标；补偿不完整时保留标记，防止当前轮的小增量更新把整体覆盖范围误判成完成。另一个保护是旧来源不能覆盖新偏好。

**追问：每次记忆调用失败都要整轮失败吗？答：**当前允许记录记忆异常并保留原记忆，避免辅助模块失败直接撤销有效回复；但不能把它解释成记忆一定已经补齐，仍要观察后续补偿。依据：C05、C08、C09、T02、T04。

### Q64｜讲一个评测设计的坑：为什么不是所有失败都算卖家问题？

**参考回答〔本批评测事实〕：**

两个原始场景把“卖家承担运费但金额未知”直接作为正式报价提交，入口拒绝是业务校验生效，不能解释成卖家 Agent 不会协商。修正后应先问运费，再在条件齐备时正式报价。

此外，买家模拟器也可能输出过长消息或违背场景规定而提前退出，这些要单独归因。当前集合保留 2 次买家模拟失败，之前真实执行的 7 个卖家轮次仍纳入轮次统计，不凭空补齐未执行轮次。

**追问：怎么避免借口“模拟器错了”删失败？答：**冻结输入契约，保留原始失败、修正理由和完整补测，以版本而不是结果选择记录，并在最终报告披露。依据：E01—E03。

### Q65｜审核一直拒绝，模型一直改写，怎么避免死循环？

**参考回答：**

已有机制包括把明确错误反馈给模型、绑定回复正文与证据缓存审核结果、限制步骤和总调用、在最后步骤收口，以及耗尽预算后的安全停止。它们保证循环有边界。

但“有边界”不代表“高效”。当前 26 次预算停止中，部分是持续攻击，部分是资料/能力边界，也有审核与职责问题。优化应按失败轨迹分类，减少同义重复修复并改善误拒；不能简单取消审核或无限加步数。

**追问：最多6步调成20步会不会立刻提高成功率？答：**没有证据。可能增加成本、延迟和重复错误；要对固定失败集比较质量与资源消耗，不能凭直觉把更多调用当成更聪明。依据：C05、C10、E04。

### Q66｜恢复功能最容易被忽略的坑是什么？

**参考回答〔复盘模板〕：**

容易只保存业务结果，没保存“执行到哪一步、已经预留多少预算、当前待处理哪些调用”。恢复时如果重置这些状态，就可能重复调用、重复写入或借重启获得新的预算。

项目检查点包含分支、步数、工具数、待执行调用、预留、摘要和记忆等；任务与工具回执一起推进。旧租约不能写，已保存模型响应可复用，业务状态变化则停止旧任务。测试需要覆盖不同崩溃位置，而不只测一次正常重启。

**追问：恢复是不是从模型的隐藏思考状态继续？答：**不是，是依据持久化输入、消息流、调用快照和检查点继续程序执行。外部模型的内部状态不在恢复范围。依据：C05、C09、C19、T04。

## 八、AI 辅助开发、个人贡献与扩展追问

### Q67｜你在项目里如何利用 AI 辅助开发？

**参考回答〔必须按本人实际经历调整〕：**

我会把 AI 用在需求拆解、备选方案、代码初稿、测试边界、故障轨迹整理和文档上。先明确业务不变量，例如聊天金额不能直接成交、未知成本不能按零、旧租约不能提交，再让 AI 围绕这些约束完成小范围工作。

我负责确认需求、审查关键控制流和验收结果，尤其检查授权、事务、幂等和指标分母。AI 输出的代码与解释都需要对照实际文件和测试；AI 能提出修复候选，不能自己宣布方案已经正确。

**追问：到底多少代码是 AI 写的？答：**如没有过程记录，不报虚构百分比。可以如实说明哪些模块借助 AI 生成、自己审查了什么，并现场讲解核心路径。仓库不能自动证明个人/AI 贡献比例。

### Q68｜给一个你会如何向 AI 提需求的具体例子。

**参考回答〔可采用的提示模板〕：**

我会给它明确范围和验收条件，例如：

> 请检查 `MemoryUpdater.apply` 对偏好变更的处理。业务要求：后到的旧证据不能覆盖新证据；两个不同待回答问题可以同时保留。先解释当前控制流，再给出最小修改和能使旧逻辑失败的测试。不要修改无关文件，不要调用真实模型，不要把买家疑问写成确定偏好。

这样比“帮我优化 Agent”更容易审查。交付后我会检查差异、运行相关测试，并核对是否误改正常路径。

**追问：上下文给得越多越好吗？答：**不是。先给目标、入口、约束和相关代码，缺失时让 AI 继续定位；无关历史会增加成本并掩盖关键事实。这个例子是协作方法模板，不声称就是本人历史原话。

### Q69｜AI 写代码再让 AI 写测试，不会自证正确吗？

**参考回答：**

会有这种风险。测试不能照着实现逐句复刻，而要来自业务不变量和失败样本。例如确认必须指向当前有效报价、未知运费不能授权、租约过期结果不能写入，都是独立于实现方式的预期。

还要使用能被观察到的外部事实验收：数据库是否只产生一条有效业务记录，旧令牌是否被拒绝，公开回复是否与实际审批一致。金额和指标可以做独立计算，检查器要加入故障注入反例；模型质量则需要独立标注和真实评测。

**追问：107 项测试通过就能证明项目没错吗？答：**不能，只覆盖本次运行的那些契约与样本。未执行的 MySQL 集成、线上负载和未知语义输入都不能算通过。

### Q70｜AI 帮你完成大部分代码，面试官为什么还应该认可你？

**参考回答〔个人贡献模板〕：**

我会用可解释和可验证的工程决策证明自己：为什么授权按净收入算，为什么事务外调用还要版本复核，为什么不能承诺 exactly-once，为什么 0 异常终止与原门禁 FAIL 可以同时成立。

如果我能现场定位相应函数，构造失败时序，解释已有局限并提出验证方法，说明我对系统负责。使用 AI 本身不是贡献证明；把生成结果变成符合需求、能够维护的系统，才是需要展示的能力。

**追问：不让你用 AI，能解释和修改核心逻辑吗？答：**应能。建议至少独立练习价格授权、幂等发送、租约接管、消息配对和指标复算五条主线；不熟悉的模块应如实说明参与范围。

### Q71｜如果再给你两周，你优先改什么？

**参考回答〔设计建议，不是已完成能力〕：**

第一，围绕已发现的审核误拒和能力承诺漏判建立独立标注集，明确任务质量标准，先修有证据的问题。第二，单独测试记忆更新失败和长对话中的偏好保持，做同版本消融。第三，补齐用户可见单轮时延和数据库/Worker 故障场景验收，再考虑减少不必要调用。

若要接真实交易平台，则另外设计明确的平台权限、商品预占、支付及履约接口、限流和数据保护，并评估接入条件。当前不能把这些未来工作写成项目既有成果。

**追问：为什么不先加多 Agent？答：**当前瓶颈有明确轨迹：审核质量、能力边界和记忆错误。增加角色未必解决这些问题，还可能增加调用和协调成本；先用证据确定是否需要拆分。

### Q72｜面试官质疑：“只有合成评测、还 FAIL，这个项目有什么价值？”

**参考回答：**

我认可它还不是生产效果证明。项目价值在于完成了有授权约束的协商闭环，并把模型调用、业务动作、失败原因和费用保存成可复核证据；这使我能具体指出哪些地方可靠、哪些地方仍不够好。

例如本批异常终止为零、正式操作检查未发现越权，但受控预算停止和语义承诺问题真实存在。我保留原 FAIL，不把它改成通过。下一步有针对性地改善这些问题，并用独立质量评审和系统集成测试验证，才有资格讨论上线。

**追问：一句话说你的最大收获？答：**Agent 的难点是把不确定的模型输出接入有边界、可恢复、可检验的业务流程，而不仅是让模型给出听起来合理的回答。
