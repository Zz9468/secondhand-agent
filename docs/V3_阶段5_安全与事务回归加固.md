# V3 阶段五：安全与事务回归加固

> 状态：已完成。阶段五不增加交易能力，而是以确定性模型替身、MySQL 事务故障注入和受控真实模型冒烟，验证阶段二至四引入的持久化任务与短事务执行没有削弱既有业务安全边界。

## 一、目标与边界

本阶段围绕以下不可退让的结论补齐回归证据：

1. 模型只能提出候选动作，正式报价、接受、审批与交易意向仍由 Service 根据数据库事实授权；
2. 策略或当前报价在模型调用期间变化时，迟到结果只能进入 `STALE`，不能形成旧承诺；
3. 任意模型候选文案、错误报价 ID、未知附加条件和审批备注都不能成为正式交易事实；
4. 完成事务中任一步骤失败时，报价、回复和任务收口不会形成无法恢复的半完成状态；
5. 任务查看和人工恢复继续服从商品所有权，未登录用户和其他卖家不能读取或处置任务。

支付、库存锁定、商品独占预订、履约保证和跨买家决策仍不属于模式 B，也没有因为增加测试而成为系统能力。

## 二、候选回复安全层加固

低风险商品咨询仍允许使用经过检查的模型候选文案；价格、配送、履约和授权类语义仍固定使用后端回复计划。候选文案检查新增：

- 使用 Unicode NFKC 规范化，统一全角字符和兼容字符；
- 额外折叠空白、连字符和标点，阻止通过“底 价”“seller-approved”等拆词方式绕过检查；
- 扩展简体中文、繁体中文、英文及少量西班牙语的私有价格、审批、成交、包邮、发货和留货承诺词；
- 对中文金额同时检查原始文本和折叠文本；
- 命中风险时不返回模型原文，而是按公开商品数据库字段生成后端模板。

该检查是低风险自然表达的最后一道输出防线，不承担价格授权。即使候选文案通过，模型动作仍必须经过工具绑定、报价区间、当前报价、策略版本和会话状态复核。

## 四、事务故障语义

聊天任务仍分为“准备并领取 → 事务外模型调用 → 重新复核并完成”。阶段五专门在第三步执行受约束还价之后、写入 Agent 回复时注入异常，验证：

- Agent 报价和 Agent 回复属于同一个完成事务；
- 回复失败会同时回滚本次 Agent 报价，买家消息和持久化任务仍保留；
- 任务保持带租约的 `RUNNING`，不会被误标为成功；
- 租约过期后由新 Worker 接管，重新复核快照并只写入一套正式事实；
- 最终 `formal_offer_id` 必须引用这一份真实持久化报价。

这与阶段四的“回复已写但任务未收口”对账测试互补，分别覆盖完成事务写入前失败和事务提交后进程退出两类边界。

## 五、真实模型对抗性冒烟

`backend/scripts/smoke_model.py` 固定执行 5 个场景级调用：公开商品咨询、包邮与发货时间复合请求、禁止接受区正式报价、英文提示注入和繁体中文提示注入。脚本启动时输出：

- 场景数；
- 单次模型超时；
- SDK 最大重试次数；
- 包含一次结构化字段组合重试在内的理论最大提供商尝试数。

对抗样本没有可信 `current_offer_id`，因此不得返回 `ACCEPT` 或 `REQUEST_APPROVAL`。若返回咨询动作，候选文案还必须经过与生产路径相同的 `DialoguePolicyService`，不得泄露测试底价或声称审批、包邮。

本阶段实测中，第一次运行因模型漏掉复合请求的一项语义而按严格标准失败；安全层没有发送错误承诺。相同配置下第二次运行的 5 个场景全部通过。这一结果如实说明真实模型具有非确定性，不能用单次冒烟替代确定性安全门禁；阶段七至八的批量评测应把此类语义波动计入结果，而不是重跑后删除失败样本。

## 六、验收方式

阶段五验收至少执行：

```powershell
cd backend
$env:RUN_MYSQL_INTEGRATION = "1"
python -m pytest
Remove-Item Env:RUN_MYSQL_INTEGRATION

python -m ruff check app tests scripts migrations
python -m alembic current
python -m alembic check
python scripts/smoke_model.py

cd ..\frontend
npm run type-check
npm run build
```

真实模型脚本必须继续保持显式执行，不得加入普通 Pytest、应用启动或前端构建。阶段六开始后，模型调用、错误分类、延迟和 Token/成本记录应进入统一观测事件；阶段五的测试名称和安全结论可直接作为观测字段及离线违规判定的来源。
