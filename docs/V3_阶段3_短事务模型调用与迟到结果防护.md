# V3 阶段三：短事务模型调用与迟到结果防护

> 状态：已完成。聊天决策与审批后续通知已经迁移到“短事务保存输入并领取任务 → 事务外调用模型 → 新短事务复核并写入”的执行方式。本阶段保留同步聊天 API 和轮询式审批 Worker；指数退避、最大尝试次数、进程重启恢复和人工处理入口属于阶段四。

## 一、目标与边界

阶段三解决两个问题：

1. 外部模型慢、超时或阻塞时，不再持有协商会话、审批、报价、商品或策略行锁；
2. 模型返回时必须重新读取并锁定当前业务事实，调用前生成的旧候选结果不能覆盖更新后的报价、规则或会话状态。

本阶段不增加新的交易业务，不改变价格授权、正式回复安全层、卖家审批或交易意向确认语义。模型输出仍然只是候选决策或候选通知，不是业务授权。

## 二、统一三段式边界

```text
短事务 A
  锁定业务入口 → 校验幂等键 → 保存不可变输入 → 创建/领取模型任务 → 提交
                                                        │
                                                        ▼
事务外模型调用
  不持有业务行锁 → 只产生结构化候选结果
                                                        │
                                                        ▼
短事务 B
  校验有效租约 → 重新锁定业务事实 → 对比版本和幂等键
      ├─ 快照仍有效：受约束工具/安全渲染 → 业务写入与任务 SUCCEEDED 原子提交
      └─ 快照已过期：不执行旧决策 → 安全通知与任务 STALE 原子提交
```

任务租约令牌同时参与完成校验。租约已经过期或被新 Worker 接管时，旧执行者只能读取当前结果，不能再写业务状态。

## 三、聊天决策链路

### 3.1 输入事务

`ChatService` 先锁定当前会话并检查买家权限和请求幂等键。新请求在同一短事务内完成：

- 保存买家消息；
- 正式报价存在时，记录不可变报价并按原有规则撤销被替换的待审批报价；
- 读取商品、会话、最近消息和报价授权；
- 确定性自动接受或进入审批的请求直接在短事务内完成，不调用模型；
- 需要模型的请求创建唯一 `CHAT_DECISION` 任务，保存完整 `DecisionRequest`、买家消息 ID 和回复幂等键后提交。

同一会话存在 `PENDING`、`RUNNING` 或 `RETRY_WAIT` 的聊天任务时，新业务请求返回“处理中”冲突，避免多个基于相同会话历史的模型结果乱序落库。同一 `request_id` 的重试会定位原买家消息和原任务，不创建重复报价或任务。

### 3.2 事务外调用与完成复核

提交输入事务后，服务按任务 ID 精确领取任务，再调用 `DecisionProvider`。完成事务至少复核：

- 租约状态、令牌和有效期；
- 协商会话版本、状态和当前报价 ID；
- 当前策略版本；
- 商品 ID、标题、描述、标价和可用状态；
- 任务关联报价归属；
- 买家消息与 Agent 回复幂等键。

复核通过后，模型结构化决策才会进入 `SellerAgent.apply_prepared`，并再次经过受约束工具、价格授权和正式回复渲染。Agent 消息、报价/审批变更及任务 `SUCCEEDED` 在同一事务提交。

复核失败时不执行模型决策，也不保存模型候选文案。系统写入不带正式报价 ID 的安全回复，并把任务置为 `STALE`。因此迟到的接受、还价或审批申请不能成为新的业务事实。

### 3.3 失败与同步 API

模型调用失败后，已经提交的买家消息、买家新报价和被其明确替换的旧审批不会回滚；任务进入 `RETRY_WAIT`，且不会写入半条 Agent 回复。客户端使用相同请求 ID 重试时继续原任务。

同步 API 保持兼容：

- 成功仍返回 `201` 和完整买家/Agent 消息；
- 同一会话已有任务运行，或任务租约已被其他执行者接管时返回 `409`；
- 模型暂时失败并可重试时返回 `503`。

前端会保留失败请求的请求 ID 和输入，相同输入再次点击发送时复用幂等键；消息轮询和响应合并均按消息 ID 去重。`409` 明确提示处理中，`503` 明确提示可安全重试。

## 四、审批后续通知链路

审批 Worker 在第一个短事务中使用 `FOR UPDATE SKIP LOCKED` 选取已审核且待通知的审批，加载可信上下文，创建或复用 `APPROVAL_FOLLOWUP` 任务并取得租约，然后提交。`SellerApprovalFollowupAgent.draft_followup` 只在事务外调用模型。

完成事务重新锁定任务、审批、会话、报价、商品和策略，并重新计算当前可信事件：

- 输入和版本未变化时，校验模型确认的事件，再由正式回复渲染器生成通知；
- 策略、商品、会话或报价在模型等待期间变化时，旧候选稿不发送，任务进入 `STALE`；
- 若当前事实能够确定原审批已经失效，则按最新数据库事实生成 `INVALIDATED` 通知并安全撤回旧报价；
- 若变化涉及新的当前报价或其他不能由旧任务推进的状态，只发送不含旧承诺的通用失效通知，不修改新的会话或报价事实。

通知消息、审批 `followup_status` 和任务终态在同一事务提交。消息继续使用审批已有的 `followup_request_id` 去重，多 Worker 不能重复发送。

## 五、失败语义与阶段四接口

聊天和审批模型异常目前使用统一任务状态记录一次失败，并设置短暂的 `next_retry_at`；这是为了提供明确的可重试状态，不是最终重试策略。阶段四必须继续实现：

- 按错误类别区分超时、限流、网络、无效结构化输出和永久业务错误；
- 指数退避、抖动、最大尝试次数和最终人工处理状态；
- Worker 进程退出及租约过期接管测试；
- 运维/卖家可查看并受控重试或终止的入口。

在阶段四完成前，不应把当前一秒重试间隔描述为生产级退避策略。

## 六、安全与幂等结论

- 模型调用期间没有打开的业务事务，也不持有会话、审批、报价、商品或策略行锁；
- `result_snapshot` 只记录通过复核的模型候选结果，不能被直接复制成正式业务事实；
- 旧租约、重复完成、不同输入复用业务键和重复回复键均不能覆盖现状；
- 确定性正式报价路径仍保持单事务原子性，回复写入失败时消息、报价和会话变化一起回滚；
- 可重试模型失败保留已经接受的买家输入，但不产生 Agent 半回复；
- 过期聊天候选与过期审批候选均进入 `STALE`，候选自由文本不会发送给买家。

## 七、自动化验收

新增或调整的 MySQL 集成证据包括：

- 聊天模型失败后输入和任务持久化、旧审批替换保持一致、任务进入 `RETRY_WAIT`；
- 阻塞聊天模型期间，另一连接可以更新策略，证明模型调用不持有热点业务行锁；
- 策略更新后旧聊天结果进入 `STALE`，不生成候选回复或正式承诺；
- 审批通知模型失败后按同一持久化任务重试，不重复消息；
- 阻塞审批模型期间策略更新可以提交，旧 `APPROVED` 候选被丢弃并按最新事实发送失效通知；
- 多 Worker 并发仍只发送一条审批通知；
- 原有正式还价、审批、幂等、权限和事务回滚测试继续通过。

阶段验收还必须运行全量 Pytest、Ruff、Alembic 当前版本与一致性检查、前端类型检查和生产构建。最终通过数量记录在本阶段提交的交付说明中，避免在文档中长期维护容易失真的测试总数。

## 八、阶段四入口

阶段四应直接复用 `model_execution_tasks` 的 `attempt_count`、`next_retry_at`、租约、错误分类和终态字段，不另建平行重试系统。聊天同步入口和审批 Worker 都应使用同一退避与错误分类策略，并补齐租约过期接管、进程重启、最大次数和人工恢复的故障注入证据。
