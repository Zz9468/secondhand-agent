## 商品资料与聊天

1. 卖家登录 → 商品管理 → 选择商品 → “商品事实与配送核实”。确认配送方式；电池及维修记录
   可保留未知。条件报价不能从描述里推断这些值。
2. 对包邮维护精确区域名称、卖家运费和其他优惠成本、失效时间。首版按区域字符串精确匹配，
   不接物流履约；重叠规则需停用多余规则后重查。仅询问买家必要区域，无需完整地址或内部成本。
3. 买家新建协商，直接输入如“电池怎么样？900 自提可以吗？”。不再提交 `offer` 对象或勾选正式报价。
   API 返回 `202`，页面轮询运行和消息，分别显示业务结果、等待前序输入、投递恢复等状态。
4. 信息不足会显示草案，回复缺失字段；备选通过具体卡片选择。未知事实/成本进入卖家核实列表。
   卖家补齐后，买家须重新明确继续；后台更新不会代表旧买家意愿直接创建报价。
5. 接受报价后，卡片被实际展示并登记回执才能点击确认。旧卡片或跨视图回执不能确认新报价。
   展示上下文到期但报价仍有效时点“刷新此方案”，重新展示后签发新回执，不延长报价。

主要接口：

| 接口 | 内容 |
|---|---|
| `POST /api/negotiations/{id}/messages` | content、request_id、client_view_id、可选展示回执及成对草案 ID/版本 |
| `GET /api/negotiations/{id}/runs/{run_id}` | 任务、业务、通知、顺序屏障状态 |
| `POST /api/negotiations/{id}/display-acks` | context_id、client_view_id、request_id；返回 display_receipt_id |
| `POST /api/negotiations/{id}/interaction-contexts/refresh` | context_id、request_id；返回同一对象的新 context_id |
| `GET /api/seller/products/{id}/evidence` | 卖家专有事实、规则、核实事项与 product_version |
| `PUT /api/seller/products/{id}/facts/{attribute}` | expected_version 与 value |
| `PUT /api/seller/products/{id}/shipping-rules` | expected_version、可选 rule_id、区域、成本、active、带时区的 expires_at |
| `POST /api/seller/products/{id}/verifications/recheck` | 重新核实并补发唯一可继续通知，不推进买家输入 |

P2 每输入冻结最多 2 次语义模型调用、50000 Token、CNY 0.20 的保守费用预算；SDK 重试为 0，
单次超时 20 秒、最大输出 2048 Token。未知费用保留预留。用户解除的是本阶段验收调用限制，
运行协议内每输入的有界配置仍保留。后续完整累计活动时间和全部辅助调用治理属于 P4。

## 真实模型校准与完整图验收

使用新项目现有配置和密钥；命令参数、终端与报告均不填写密钥。每次指定新的报告文件名，
避免覆盖失败或成功证据。在 `backend/` 执行：

```powershell
..\.venv\Scripts\python.exe -m scripts.probe_p2_semantics --allow-real-model `
  --max-calls 0 --max-cny 0 --output ../artifacts/p2/recheck-live-core.json
..\.venv\Scripts\python.exe -m scripts.probe_p2_semantics --allow-real-model `
  --dataset evaluation/datasets/p2_semantic_extended.json --max-calls 0 --max-cny 0 `
  --output ../artifacts/p2/recheck-live-extended.json
..\.venv\Scripts\python.exe -m scripts.run_p2_live_tests --allow-real-model `
  --output ../artifacts/p2/recheck-live-graph.json `
  --junitxml=../artifacts/p2/recheck-live-graph.xml
```

字段校准包含基本集 20 条和扩展集 21 条合成文本，不写业务数据库；参数 0 表示该批次不限次数或金额，
省略参数时仍默认为 30 次和保守预留 ¥1。脚本无 SDK 隐式重试，结构/原文验证失败最多修复一次；
每次调用前持久化预留，记录提示词版本、
源码提交、模型、耗时、用量和结果。无法计价的配置仍拒绝调用，不猜费用。

完整图验收使用相同真实模型适配器和业务调用账本，在随机临时 MySQL/PostgreSQL 库中运行，
覆盖多轮草案、资料核实、备选选择、展示确认、刷新因果、撤回与关闭。报告保留每轮实际模型结果、
业务动作、轮次、回复和账本摘要，失败时也保存；结束后仅清理本次临时数据库。
不要同时启动两份 `run_graph_tests` / `run_p2_live_tests`，它们共享独立 PostgreSQL 集群的清理角色。

当前提示词为 `p2-intents-v8`，适配器保留 v1～v7 的原文和输出模式以恢复旧冻结输入。
v7 起启用 JSON Schema；仍执行本地结构、原文和业务检查。v8 的一次结构修复也走原调用账本，
共用每输入 2 次/50000 Token/CNY 0.20 上限，校准断言失败或业务拒绝不会触发该修复。
字段校准与完整业务图
必须分别通过；本阶段开发样例不能替代 P5 独立保留集、统计风险门槛或生产许可。

数据库回退只验证空临时库；有 P2 草案、重复刷新上下文、业务回执或待通知数据时保留表和证据，
停止新输入并恢复相应版本 Worker，不在业务库直接 downgrade 或删除 checkpoint。
