## 1. 目标与适用范围

先完成影响交互可靠性和演示体验的开发修复，再进入云端部署。目标环境仍是“预约、有人值守、少量受邀用户”的面试演示，系统完成交易意向确认，不包含支付、库存锁定或真实订单履约。

本轮开发目标：

1. 请求遇到断网、响应丢失或页面刷新后，可以核对原操作结果，避免因重新生成请求 ID 而重复入队。
2. 页面正确区分请求提交、任务执行、业务结果、通知交付和人工恢复状态。
3. 减少连续点击和状态不清造成的重复操作，并保留已有 FIFO、队列上限和合法操作能力。
4. 复现并定向处理明确的语义误判，保留必要的澄清与安全兜底。
5. 形成绑定实际提交的本地交付验证记录，满足第 8 节条件后转入部署。

本地 MySQL/PostgreSQL、容器、浏览器和故障注入测试属于开发验证。云服务器采购、域名、Nginx、证书和云端恢复演练在后续部署阶段实施。

沿用已有双库、API、Worker 和 watchdog 的分工。优先复用现有输入记录、幂等约束、状态查询、展示凭据与审计记录；新增数据库结构必须先说明现有结构无法满足的具体需要。

此前暂缓的独立代表性评测集、正式 AI 质量评测人工复核、LangSmith 远端完整性验证、正式时延与成本标准继续暂缓。本轮开发者检查故障和少量交互样本，不代表解除这些正式验收事项。

## 3. 修复过程中必须保持的约束

1. **幂等以原操作身份和完整载荷为准。** 重试沿用原请求 ID、操作类型和原始字段；修改输入属于新意图，不能套用旧请求 ID，也不能按文本相同就合并两次独立意图。
2. **本地缓存只是恢复线索。** 服务端账号、会话所有权、输入记录和业务回执决定真实结果；缓存不能授予权限或证明业务完成。
3. **展示授权继续有效。** 已接受操作的核对或幂等重放保留原视图与回执；新的确认必须使用当前有效展示依据。不得全局复用旧视图来绕过确认条件。
4. **业务、执行、通知分别判断。** HTTP 202 代表接受输入；任务成功不自动证明通知完成；等待卖家审批也不是运行故障。
5. **重放不创建额外执行机会。** 相同输入重放不新增任务；卖家相同恢复请求不重复增加恢复次数，不重置原预算。故障恢复仍可能按既有协议重试模型，不能据此承诺供应商侧绝对只计费一次。
6. **FIFO 和审计继续生效。** 不通过跳过队首、清空表、删除 checkpoint、删除回执或重置预算消除错误。
7. **失败证据如实保留。** 未知用量不按零记录；局部回归不包装为独立泛化测试；旧提交通过记录不替代本次修改的验证。

推荐按阶段提交，确保每个修复可以独立检查。D0 的失败用例贯穿后续阶段；后续修改影响前序能力时补跑相关测试。

| 阶段 | 对应问题 | 主要交付物 | 前置条件 | 完成判据 |

| D0：固定基线与复现 | DEV-01～07 | 问题复现记录、测试入口、故障场景 | 代码基线已核对 | 已确认问题能复现，待核查问题有检查方法 |
| D1：请求结果核对与恢复 | DEV-01、02、05 | 只读查询、请求保存模块、买卖家接入、权限测试 | D0 | 响应丢失、刷新和重复提交通过幂等验证 |
| D2：异步状态与轮询 | DEV-03 | 状态判定、轮询收尾/恢复逻辑、通知故障测试 | D1 | 页面状态随服务端结果更新，不提前宣告完成 |
| D3：提交节奏与交互 | DEV-04 | 防重复点击、结果未知提示、排队提示、队列验证 | D2 | 不误锁合法操作；连续输入和阻塞状态可理解 |

### 4.1 D0：固定基线、复现问题并准备测试

- 记录实际提交、工作区状态、模型组合和测试环境；使用本次隔离测试数据，避免依赖历史会话的偶然状态。
- 先复现“已接受但响应丢失”，不能只模拟请求发送前断网。浏览器测试要能让后端完成接收，再丢弃返回给页面的响应。
- 补充最小必要的前端状态测试与浏览器测试入口，锁定测试依赖，并记录实际运行命令。现有前端没有这些命令，不能提前写成已经可以执行。
- 将请求保存/恢复和状态判定抽成可测试逻辑，Vue 页面负责展示与交互；避免把核心恢复流程继续分散在多个页面变量中。
- 基础用例使用替身模型；后端一致性、事务和恢复用例使用既有隔离双库测试机制。

**阶段验收：** 第 6 节每个场景标记为“已复现缺陷”“现有行为通过”或“待实现测试”，记录原因。前端交互测试必须能够发现原有恢复缺口。

### 4.2 D1：实现可靠的请求结果核对与重试

#### A. 服务端只读查询

计划增加 `GET /api/negotiations/{session_id}/requests/{request_id}`，按当前登录买家、会话和请求 ID 查找既有输入，返回其 `run_id` 与允许公开的执行、业务、通知状态。

- 复用 `NegotiationInput` 的 `(session_id, request_id)` 唯一约束和 `GraphStatusService` 的公开状态定义。
- 查询不创建输入、不续租、不恢复任务、不调用模型，也不返回内部载荷、卖家底价、私密策略或执行凭据。
- 未登录拒绝访问；无权访问和不存在的对象保持不泄露归属的返回方式。
- “暂未查到”不能证明原请求永远不会落库：若原请求仍在途，只允许沿用同一请求 ID 和完整载荷进行受控重试，不能创建替代 ID。
- 对卖家恢复操作，复用 `GraphRecoveryAction` 审计记录设计受当前卖家保护的只读结果核对。审批操作先检查已有详情与请求回执是否足够；确有缺口再补相应查询。

#### B. 前端请求保存与恢复

建立共享模块，至少记录：格式版本、账号 ID、会话或操作目标、操作类型、请求 ID、完整原始载荷、创建时间、客户端提交状态，以及已知的 `run_id`/服务端结果标识。

- 默认使用按账号和会话隔离的 `sessionStorage`，支持同一标签页刷新、页面切换和短暂断网后的恢复。关闭标签页或换设备后的待发送请求自动恢复不属于本轮承诺范围。
- 请求发出前完成持久化；收到结果后更新记录。发送前保存失败时，不发起本次写请求，并提示存储不可用。已经拿到成功响应时，后续缓存写入异常不能被误报为“后端没有接受”。
- 网络异常进入“结果待核实”，保留原请求，不因刷新、超时或用户再次点击而自动生成新 ID。
- 页面恢复后，已知 `run_id` 直接查询状态；只有请求 ID 时先查询接受结果。无结果且仍满足重试条件时，通过明确的重试动作重放原请求，避免无限后台重试。
- 400/409/422 等响应按具体含义处理；载荷冲突或失效展示凭据不能通过更换 ID 自动重试。需要新操作时重新展示并由用户明确发起。
- 缓存带格式校验、保留期限和数量上限。异常缓存不能阻断服务端历史读取；不能因缓存过期或损坏自动推断旧操作失败。
- 账号切换/退出时清理或隔离旧账号缓存，终止旧页面恢复流程；晚到响应不得写入新账号页面。严禁用新账号 Cookie 自动重放旧账号请求。
- 已完成记录及时移除敏感载荷，运行结果从服务端重新读取。浏览器缓存不保存口令、Cookie、模型 Key 或卖家私密策略。

#### C. 接入范围与验证

先接入买家消息、方案选择、确认和关闭，再接入卖家恢复；审批操作根据 D0 复现结果补齐相同能力。新的用户意图仍可获得新请求 ID，但必须与尚未核实的旧操作明确区分。

**阶段验收：** 响应丢失后刷新可找回原操作；原请求重复提交不新增 `NegotiationInput`、业务回执或恢复审计动作；查询接口本身不产生模型调用；跨账号、跨会话及载荷变化请求被拒绝或安全隔离。

### 4.3 D2：统一状态展示与轮询生命周期

以服务端的 `task_status`、`business_status`、`notification_status`、`blocked_by_input_seq`、`recovery_required` 和会话状态共同决定页面行为。

| 状态情形 | 应展示的信息 | 更新策略 |
|---|---|---|
| 提交结果未知 | 网络异常，正在核对原操作 | 查询原请求；不宣告失败或重新生成操作 |
| 已接受、尚未执行 | 已排队；被前序输入阻塞时说明原因 | 继续查询，不承诺未经测量的预计完成时间 |
| 正在执行 | 正在处理 | 持续同步任务与消息 |
| 自动重试等待 | 暂时失败，等待后台重试 | 沿用原任务跟踪，不创建新任务 |
| 等待审批 | 等待卖家处理 | 同步会话和审批结果，不误标为系统故障 |
| 业务已提交、通知未完成 | 业务结果已记录，通知恢复中 | 继续跟踪通知，禁止重新执行相同业务来补消息 |
| 需要人工恢复 | 明确需要卖家处置，原输入保留 | 保留刷新/适当低频同步，恢复后能继续更新 |
| 已完成 | 展示最终公开结果 | 按执行和交付契约停止该输入的活跃轮询 |

实现时不得仅用 `task_status === 'SUCCEEDED'` 停止跟踪，也不能把所有 `NOT_REQUIRED` 都理解为通知已完成：执行早期可能还没有生成通知记录。应结合输入是否真正结束以及该路径是否存在交付义务判断。

补充网络恢复、页面重新可见时的状态同步，处理临时查询失败和退避；页面卸载或会话切换时停止旧轮询，忽略不再属于当前页面的返回。终态输入的轮询结束不影响仍需更新的会话或审批状态。

**阶段验收：** 任务成功但通知延迟、通知恢复成功、人工恢复后继续执行等场景均能更新；页面不会长期停在旧状态，也不会把暂时断网显示为业务失败。

### 4.4 D3：改善连续提交、排队与异常提示

- 提交中阻止相同按钮重复发起请求；结果未知时先提供原操作核对和重试入口。
- 显示当前未完成输入及阻塞原因；保留尚未发送的文本，避免一次请求结束清掉用户后来输入的内容。
- 按操作是否允许决定按钮状态，而不是把整个会话一直锁到 `AGREED`。等待审批时按既有规则保留修改/关闭能力；队首失败时仍可进入卖家恢复流程。
- 把队列已满、请求限流、登录失效、展示过期和需要人工恢复分别提示。前端防重复点击不能替代服务端幂等和队列保护。
- 在登录页和商品/协商入口补充虚拟演示、仅交易意向、避免真实个人资料的说明，并给出清楚的体验步骤。

默认保留已有单会话 20 条未完成输入保护和一个 Worker。先测单用户及少量重叠输入的等待与恢复；若出现持续积压，再单独增加可配置的接收上限。新增上限必须由服务端原子检查，幂等重放不重复占用配额，修改后回归 FIFO 和确认边界。

**阶段验收：** 连续点击不会新增同一操作；用户能理解等待原因并继续合法操作；既有队列上限有效；没有把“降低入口频率”当作全站模型费用上限。

### 4.5 D4：语义质量归因与定向修复

优先检查 [semantic/service.py](../backend/app/semantic/service.py)、[semantic/quality.py](../backend/app/semantic/quality.py)、[semantic_graph.py](../backend/app/graphs/negotiation/semantic_graph.py) 及 [test_p4_quality.py](../backend/tests/graph/test_p4_quality.py)。

1. 固定模型、配置与商品授权，复现“提交报价被理解为最终确认”等历史问题，区分模型输出、解析校验、业务路由和质量审查各环节。
2. 将兜底分为：合理的授权/证据不足或真实歧义；明确输入被误解；模型/结构化输出/审查运行异常。只修改已定位原因。
