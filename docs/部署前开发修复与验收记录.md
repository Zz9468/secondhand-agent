**原因与实现决策**

1. **请求恢复缺口已经动态确认。** `pending` / `pendingButton` 仅保存在组件内存，`remember()` 在收到 202 后才保存 run_id。浏览器先通过 `route.fetch()` 让真实 API 完成事务，再 `route.abort()` 丢弃返回，刷新后同一尝试生成新 ID，消息输入 1→2、确认输入 1→2。测试没有执行这两次排队确认，不能把“重复入队”扩大成“重复成交/收费”。D1 应保存完整原始载荷和原视图，不根据文本相同合并独立意图。
2. **存储异常与提交顺序。** `setItem` 被注入失败时，后端已有输入；当前 catch 显示错误，不能证明未接受。损坏缓存的 JSON 解析也会抛出。D1 分开处理发送前保存和已接受后的缓存失败，补格式、TTL、数量及账号隔离；D0 未设计新缓存协议。
3. **状态缺口。** 把现有 `outcome`、轮询判定及 run_id 缓存读写原样提取到 `runTracking.ts`，供页面和单测共用，行为未修复。`SUCCEEDED` 直接停止 run 查询，无法跟进合成的待通知→已发布状态。D2 需要结合执行、业务、通知与人工恢复判定。真实双库通知测试与合成页面组合分别报告，未声称该组合已经在真实 Worker 自然产生。

**根因、实现决策与接口契约**

1. **查询复用既有记录。** 买家新增 `GET /api/negotiations/{session_id}/requests/{request_id}`，复用 `NegotiationInput` 唯一约束与原有公开运行状态投影。卖家恢复新增 `GET /api/seller/graph-recovery/{target}/requests/{request_id}`，读取 `GraphRecoveryAction`；审批新增 `GET /api/seller/approvals/{approval_id}/requests/{request_id}`，读取 `BusinessActionReceipt`。审批详情只说明对象状态，不能确认当前 request_id 是否已接受、是否仍在途，因此补准确回执查询。三个查询都只读，不加执行锁、不续租、不触发模型、不增加恢复机会；未登录 401，其他账号/对象或未找到统一 404。不返回原载荷、原视图/展示凭据、私密策略或执行凭据。
2. **共享持久化与恢复控制。** `pendingOperations.ts` 定义版本 1，sessionStorage 键为 `secondhand-operations:v1:<账号>`，每条含账号、目标、类型、requestId、创建时间、提交状态和完整原载荷；买家已接受记录保留 runId。记录按目标筛选，保留 24 小时、每账号最多 100 条；超量优先移除已接受/明确拒绝的元数据，不能为新请求静默挤掉未核实记录。格式、字段白名单、类型、时间、账号和大小校验；损坏/过期只显示核对历史的提示，不阻断服务端历史读取、不声称业务失败。
3. **发送和重试次序。** 首次 POST 前必须持久化成功，存储不可用就不发送；网络/5xx 保留未知结果。刷新只查询，已知 runId 查原运行，否则查原请求；404 不证明原请求不会落库。只有明确点击“重试原操作”才重放完整原始 body，保留 view、receipt、draft/version、审批 revision/comment、恢复 action/reason；不自动改 ID，不后台自动 POST。已有未知操作时提示先核对，用户可明确选择“另行发起新操作”，旧操作继续保留；已接受的相同文本再次发送是独立新意图，不按文本去重。
4. **失败与接受分别处理。** 400/403/404/409/422/429 按拒绝处理，409 先查询原记录；不会静默换 ID。若重试被拒绝而原提交仍可能在途，保存 `blocked` 的原请求身份，停止重放但保留核对入口；其后原请求落库仍能恢复。接受后立即移除原载荷，只保留核对元数据；缓存写入或后续历史读取失败仅提示“已接受但本地更新失败”，不把它变成发送失败。`blocked` 的记录也不被数量淘汰。
5. **身份和页面代次。** 认证变化递增版本，退出/切账号清理旧账号缓存；页面/会话恢复流程使用认证版本与组件代次，忽略旧结果，包括 A→B→A。共享 Cookie 可能先于广播改变，因此 `requestJson` 在已登录的业务请求附加可选 `X-Expected-User`；服务端比对 Cookie 主体，不匹配返回 401，头部本身不授予权限。旧请求晚到的 401 不影响新认证版本。账号变更重建 RouterView，卖家读结果也校验认证版本；登录等待本标签页未完成的退出请求，避免旧退出响应清掉新 Cookie。
6. **买卖家接入。** 买家消息、方案选择、确认、关闭，以及卖家审批同意/拒绝、任务重试/终止/通知恢复共用 `usePendingOperations` 和核对面板。恢复核对不依赖“当前可恢复任务”仍在列表中；操作消失后仍可凭审计确认结果。原有按 sid 缓存 runId 的旧键不再读取：旧键无账号、无原载荷，不能迁移成安全重放依据；旧服务端历史仍可读取。
7. **保留协议与阶段边界。** 未修改入队、展示授权、确认业务、FIFO、队列 20 条、预算、Worker/watchdog 和审计写协议。已接受确认重放可保留原 view/receipt；新确认仍从当前卡片生成依据。D2 的通知轮询结束判定与 D3 的新草稿被旧响应清空仍保留预期失败，未在本阶段修复。没有真实模型、完整 D5 交付、云部署或远端 CI。
8. **测试独立性。** 浏览器夹具改为真实 Cookie 登录；使用新建随机双库和合成账号，测试入口与暂停闸门只存在 `test_predeploy_browser.py`，绑定回环临时 API。暂停实际 enqueue/审批/recovery 调用后再刷新和重试，验证原请求仍在途时的 404 与单次接受；不把“发送前断网”替代“后端已提交后丢响应”。真实 provider 继续被阻断；替身 token/cost 不算真实费用。

3. **轮询独立于输入结束。** 新增 `polling.ts`：每代页面串行发起读周期，正常间隔 2 秒，仅剩人工恢复输入时为 10 秒；读取失败退避为 4/8/16/30 秒并封顶，成功后恢复正常频率。GET 15 秒超时取消，停止/换页/换账号中止旧请求并使旧回调失效；旧请求最终结束不会释放新页面的锁或覆盖其状态。单周期内消息、会话和各运行读取独立应用成功结果，某一失败不阻塞其他结果；错误只显示同步中断，不判定提交失败。
4. **在线与可见性恢复。** 隐藏或离线时暂停读周期，恢复在线/可见时立即同步；初次加载失败也可自动重试。唤醒时对尚未恢复为运行状态的本地原操作做只读核对，继续复用 D1 的账号/页面保护与显式 POST 重放。卸载移除监听器。终态输入不再查询自身，但消息/会话查询继续，因此审批及 CLOSED/AGREED 后的通知仍能更新。
5. **真实回归发现并修复加载竞态。** 将历史与详情拆为独立读取后，历史先返回时聊天容器尚未挂载，早到的滚动调用无效，卡片可见比例不足，R05 的确认/方案按钮持续禁用。首次完整浏览器检查发现 3 项失败。修复为详情首次挂载后再次执行初始滚动并登记可见卡片；消息后到时仍由消息更新滚动。未放宽 IntersectionObserver 的可见条件、未伪造展示回执、未复用旧视图。最终完整浏览器复验覆盖这 3 项。
6. **真实故障与合成覆盖分列。** 测试专用回环夹具在真实 GraphRunner 的 `after_command` 中断后观察 `COMMITTED + RETRY_WAIT + PENDING`；独立通知真实发布抛错三次，经现有 `claim/retry` 到 `MANUAL_REQUIRED`，真实 Cookie 卖家 NOTIFY 后再发布和收尾，仍为同一输入、回执和通知。人工恢复通过 `after_claim` 的 RecoveryConflict 注入，经真实卖家 RETRY、原输入重跑及 FIFO 后继完成；审批由真实 GraphApprovalService/ApprovalRunner 应用。只有两个明确标记的页面用例替换公开 GET 结果，不能替代协议可达性证据。
7. **阶段约束。** 未修改业务入队、FIFO、20 条上限、预算、Worker/watchdog、审计或确认授权。所有模型使用既有替身并拦截真实 provider；D3 新草稿被较早响应清空继续保留预期失败，不借此扩展本会话范围。

1. **草稿归属。** 原 `onAccepted` 对任何消息/方案成功或查询恢复均无条件清空 `text`，会删除后输入的文本，选择方案也会误清输入框。现在以请求编号绑定编辑版本：只有原文本在提交后未被编辑时才清空；编辑后改回相同文字仍视为新草稿；方案选择不绑定文本。拒绝/未发出的记录清理绑定，未知结果保留到核对，切换页面清除绑定。没有按文本合并意图；同文本再次明确发送仍创建独立请求。未发送草稿仅在当前挂载页面保留，没有新增跨刷新草稿存储承诺。
2. **按钮与合法操作。** 沿用共享 `operationBusy` 同步守卫，覆盖鼠标和 Ctrl+Enter；确认与关闭还会根据已接受原操作的运行状态抑制执行期间重复点击，并在刷新恢复后维持。确认处理函数再次检查当前卡片有效性。按操作控制，未把整个会话锁到 AGREED；等待审批时修改报价/关闭均经真实 API + GraphRunner 执行验证。
3. **等待提示。** 显示“本页跟踪的未完成输入”数量及按序处理提示；沿用 D2 的执行/业务/通知分类，按输入序号排列状态。人工恢复说明指向“卖家模式 → 恢复任务”，保留原输入及后继等待原因；审批提示明确仍可修改和关闭。此数量只统计本标签页已保存并核对的操作，不是其他标签页/设备的全局队列计数，不显示未经测量的 ETA。
4. **错误分类。** 新 `operationFeedback.ts` 在既有 HTTP 状态及公开 detail 文本上区分队列满、429 和展示/草案失效，其他冲突保留原解释，不改变重试决策。409 仍先查原回执；未知/blocked 的 D1 规则不变，不自动换编号或重发。首次明确拒绝后移除此前 404 的临时“可重试”提示，避免与 rejected 状态冲突。当前 API 没有结构化错误类别，若将来修改公开错误文本，需同步映射和测试。
5. **登录失效。** 认证层在已有身份收到 401 时设置内存提示，跳到登录页后解释重新登录、检查历史以及不能据此认定原操作失败。登录成功/主动退出清理提示；没有保留旧账号写权限或用新 Cookie 重放旧请求。D1 的账号缓存隔离/清理继续生效。
6. **刷新方案竞态（本次测试定位并修复）。** 首轮定向浏览器 12 通过、1 失败：后端将展示上下文置为过期后，第一次确认正确被拒绝；点击刷新时旧回执仍可用，第二次确认赶在刷新返回前再次带旧回执，被后端拒绝。现在刷新一开始撤下本地旧回执、禁止重复刷新和旧上下文展示登记，等待新上下文真正可见并取得新回执后再启用确认/方案选择。服务端展示授权未放宽，最终用延迟刷新响应及强制 click 验证窗口关闭。
7. **演示边界。** 共享 `DemoNotice.vue` 覆盖登录、商品大厅、商品详情和协商入口：虚拟演示、仅记录意向、无付款/库存锁定/履约、不要填写真实个人资料，并列出完整体验步骤。操作编号折叠展示，未知结果优先引导核对和原操作重试。
8. **容量和兼容性。** 保留单会话 20 条未完成输入与单 Worker。两条重叠输入按 FIFO 完成，人工恢复后后继继续，满队列拒绝新请求但同 ID 重放仍 202；这不是持续负载/吞吐或全站费用上限证明，没有据此收紧接收限额。无生产后端接口、错误码、数据库迁移、配置、依赖、缓存版本、预算或审计规则变化。仅测试夹具新增过期上下文注入及 product ID 返回；不进入生产应用。

**复现、归因与实现决策**

1. **真实解析误判，不是业务审批故障。** 原 P6 句“我出800元，自提，现在提交这个报价。”在本次基线恰好通过；相近句“请提交我的报价：800元自提。”真实复现 `PROPOSE_OFFER + CONFIRM_INTENT`。结构校验通过，`plan_turn` 按两个动作冲突规划为 QUERY，未写报价/审批回执。基线 3 项中 2 通过、1 失败；没有将原历史句的一次通过写成问题消失。证据：`live-baseline.json/xml/log`。
2. **确认防线确有缺口。** 替身仅返回 CONFIRM_INTENT、引用“现在提交这个报价”或从否定句中截出“确认”时，在有效旧报价 DisplayAck 上可写 `INTENT_CONFIRMED`。修复前单测 4/4 失败、真实双库反例 4/4 失败；这是注入错误模型输出的确定性证明，不声称真实模型本次曾误成交。最终复核另加“我不同意。”/“不接受。”的截断引用反例，在 v3 上仍有 2 项单测失败（`veto-review-before.log/xml`：7 通过、2 失败），将原有否定模式也改为检查整条输入后关闭。`safe_frame` 现在同时检查整条输入的明确否定及提交报价措辞，只否决确认，绝不把错误帧转换成默认报价、丢弃冲突动作或补充授权。
3. **分版本修订语义提示词。** `p5-intents-v2` 首先区分报价提交与最终确认；首轮真实复验又发现“改成900元包邮到上海，请提交修改后的报价。”被拆成 CHANGE_TERMS 与额外缺少 candidate 的 PROPOSE_OFFER。两次结构校验均拒绝，安全澄清。最终默认 `p5-intents-v3` 明确“修改＋提交”为同一动作，仍保留条件、真正冲突和原文依据校验。原有全部提示词与本轮 v2 保留，旧版本的结构化格式/一次修复尝试保持；核对见 `frozen-prompt-check.json`。
4. **审查引用错误与业务错误分开修。** v2 实测审查有时给出 approved=true，却把候选改写句而非 `items[].text` 放入 evidence_quotes；程序正确拒绝。也观察到审查要求将“已接受、待确认”进一步解释成交易达成。新增 `p4-v3` 审查提示明确引用来源、合法的未知/澄清结果和逐项语义覆盖，仍经过原有覆盖 ID、证据子串、数值、私密信息及越权承诺校验。未修改 `candidate_safe` 或放宽 `review()`；新增自引候选、漏 ID 的反例验证仍拒绝，报价回执只写一次。
5. **测试预期也如实纠正。** 首轮真实复验的未知维修条件已正确保留“如果没修过”、UNKNOWN 和原条件，但测试误要求出现“维修”二字，改为核对草案结构。另一测试误以为过期回执会入队后澄清，实际入口已抛 Conflict；改为断言入队拒绝，并另增“入队后才过期”的真实模型反例。保留原失败，不当作产品修复成果。正向确认断言使用业务结果 `INTENT_CONFIRMED`，会话终态为 AGREED。
