**原因与实现决策**

1. **请求恢复缺口已经动态确认。** `pending` / `pendingButton` 仅保存在组件内存，`remember()` 在收到 202 后才保存 run_id。浏览器先通过 `route.fetch()` 让真实 API 完成事务，再 `route.abort()` 丢弃返回，刷新后同一尝试生成新 ID，消息输入 1→2、确认输入 1→2。测试没有执行这两次排队确认，不能把“重复入队”扩大成“重复成交/收费”。D1 应保存完整原始载荷和原视图，不根据文本相同合并独立意图。
2. **存储异常与提交顺序。** `setItem` 被注入失败时，后端已有输入；当前 catch 显示错误，不能证明未接受。损坏缓存的 JSON 解析也会抛出。D1 分开处理发送前保存和已接受后的缓存失败，补格式、TTL、数量及账号隔离；D0 未设计新缓存协议。
3. **状态缺口。** 把现有 `outcome`、轮询判定及 run_id 缓存读写原样提取到 `runTracking.ts`，供页面和单测共用，行为未修复。`SUCCEEDED` 直接停止 run 查询，无法跟进合成的待通知→已发布状态。D2 需要结合执行、业务、通知与人工恢复判定。真实双库通知测试与合成页面组合分别报告，未声称该组合已经在真实 Worker 自然产生。
4. **交互缺口。** HTTP 提交窗口内 busy 能抑制重复发送；但是提交成功无条件 `text=''` 会删除用户后来输入的草稿。D3 解决该问题及队列/重试提示；当前未见支持收紧 20 条上限的负载证据，保留原保护。
5. **卖家操作区别处理。** 已接受的审批丢响应后，刷新现有详情即可看到 APPROVED，决定事件仍 1；不预先新增审批查询接口。恢复操作刷新后任务列表为空，既无原 ID 又无操作核对结果，虽然本次审计和 manual_retry_count 均为 1，D1 仍需受卖家所有权保护的审计查询。未提交/仍在途、切账号、审批刷新前重试窗口尚需补测，不能以单个窗口通过关闭整个 DEV-05。
6. **测试设施与隔离。** 使用固定版本 Vitest 5.0.5、Playwright 1.64.1；Node 类型依赖也精确锁定。Playwright 针对真实 Vue 页面；pytest 复用既有 `graph_factory` / `scripts.run_p0_tests` 随机双库，临时回环 FastAPI 注入夹具身份及替身 provider。种子/只读观测路由只存在测试文件，不进入生产应用。真实 provider 被拦截并计数；无生产 Worker。身份夹具不等价于真实 Cookie 登录或切账号验收。
7. **失败不能被绿色汇总掩盖。** 预期失败仅在对应最终业务断言前标注；建库、真实 202/200、入库数量等前置检查必须正常通过。独立 reporter 输出 `outcomes.json`，明确通过/预期失败/意外结果；禁止把 Playwright 默认的“11 passed”解释为 11 个功能通过。修复后必须移除对应预期失败标记，否则意外通过会使套件失败。
8. **兼容性。** 未增加生产 API、错误码、数据库迁移、业务配置、缓存格式或预算规则。唯一产品代码变化是等价提取状态/缓存逻辑。新增测试、类型检查、CI 步骤；完整持久化请求恢复模块留 D1。保留 FIFO、幂等、展示授权、审计和预算约束。
