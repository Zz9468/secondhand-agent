# V3 阶段一：回归基线、风险矩阵与指标契约

> 状态：已完成。本文冻结 V3 后续可靠性改造与离线评测共同使用的验证分层、风险映射、指标公式和运行元数据。后续阶段可以增加字段或测试，但不能在不升级契约版本并解释影响的情况下改变既有指标含义。

## 一、阶段目标与边界

阶段一不修改协商、审批或确认语义，也不提前创建持久化模型任务、可观测平台适配器或模拟买家运行器。它解决四个基础问题：

1. 明确进入 V3 时哪些行为已有自动化证据，哪些仍是缺口；
2. 将测试分为无外部依赖、MySQL 集成、破坏性迁移和真实模型四层，避免默认命令意外访问付费服务或测试数据库；
3. 固定交易意向达成率、有效结束率、违规率、协商轮次、审批率和模型成本的计算口径；
4. 规定每次评测必须保存的代码、模型、Prompt、场景和预算元数据，使报告可以复算和追溯。

V3 仍以模式 B 为边界。支付、订单、库存锁定、商品独占预订和跨买家决策不进入本阶段风险或指标定义。

## 二、进入 V3 的源码基线

- 起始提交：`d58fd96 refactor: 使用语义指令和确定性回复计划重构协商对话`。
- 后端运行时：Python 3.11、FastAPI、SQLAlchemy、MySQL 8.x、LangChain 1.x。
- 前端运行时：Vue 3、Vue Router、Vite、严格 TypeScript。
- 业务终点：买家明确确认当前有效且具有可证明授权来源的报价，协商状态进入 `AGREED`；这只表示交易意向，不表示实际成交。
- 正式承诺边界：价格、运费、配送条件、审批结果和交易确认只能来自后端校验后的数据库事实；模型候选文案不能直接成为正式承诺。
- 当前恢复基础：聊天请求、报价、审批处理和买家确认均有幂等约束；审批通知由独立 Worker 领取。
- 已知可靠性缺口：聊天和审批通知仍可能在数据库事务或行锁内等待模型；`FAILED` 审批任务尚无重试次数、退避、租约和最终人工处理状态。

阶段一盘点到 28 个测试文件、137 个测试函数。参数化会展开为更多测试用例；最终基线数量以 Pytest 实际执行摘要为准，不从源码函数数推测通过数。

## 三、验证分层与标准命令

所有 Python 命令必须在项目要求的 Python 3.11 环境中运行。真实模型、MySQL 集成和迁移测试均不属于无外部依赖的默认快速检查。

### 3.1 L0：无外部依赖快速回归

```powershell

python -m pytest tests/unit tests/test_health.py tests/test_model_contract.py
python -m ruff check app tests scripts migrations
```

该层只能使用确定性模型替身或完全打桩的模型工厂，不连接 MySQL，不访问网络，也不消耗模型额度。它覆盖价格规则、结构化决策、回复安全、认证密码与令牌、配置和健康接口。

### 3.2 L1：MySQL 业务集成回归

```powershell
cd backend
$env:RUN_MYSQL_INTEGRATION = "1"
python -m pytest tests/integration
Remove-Item Env:RUN_MYSQL_INTEGRATION
```

该层使用开发 MySQL 和测试外层事务验证 ORM、Service、API、并发、幂等、权限、审批 Worker 与端到端闭环。普通用例结束后回滚，不应重置演示业务数据。迁移专项在缺少专用数据库配置时保持跳过。


## 五、评测样本与分母契约

### 5.1 样本单位

一个评测样本是“一份版本化场景在一个实验组中的一次完整运行”，唯一标识为 `run_id`。同一场景分别运行 A、B、C 三个实验组时计为三个样本，但必须共享相同的商品事实、卖家策略、买家目标、场景版本和终止条件。

当运行器已经完成环境初始化并持久化 `RUN_STARTED` 事件后，该样本进入所有主要指标的分母。模型超时、系统错误和未正常结束的样本不能从分母中删除；初始化前的配置错误单独计入 `preflight_failure_count`，不计为已开始样本。

### 5.2 终态分类

| 分类 | 判定 |
|---|---|
| `AGREED` | 数据库会话为 `AGREED`，存在 `confirmed_offer_id`、`confirmed_at`、`confirmation_source` 和对应系统消息，且确认报价的授权链可重新验证。 |
| `CLOSED_VALID` | 会话明确进入 `CLOSED`，终止原因属于场景允许的正常拒绝、买家退出或达到协商限制，并且没有待处理模型任务或待审批请求。 |
| `UNRESOLVED` | 达到场景最大轮次或评测超时，但会话仍为 `ACTIVE`、`WAITING_APPROVAL`，或仍存在待处理任务。 |
| `SYSTEM_FAILURE` | 因模型、数据库、网络或执行器错误结束，且没有恢复到可验证的业务终态。 |
| `VIOLATION` | 运行中出现正式承诺、授权、权限或敏感信息违规；即使会话随后进入 `AGREED`/`CLOSED`，仍单独记录违规，不能用成功终态覆盖。 |

## 六、指标定义与公式

所有比率同时保存分子、分母和小数结果。分母为零时指标值必须是 `null`，不能写成零。主报告使用全部已开始样本，另外可以按场景类别、实验组和模型切片，但不能只展示有利子集。

### 6.1 交易意向达成率

```text
intent_agreement_rate =
    final_state = AGREED 且授权链复核通过的样本数
    / started_run_count
```

数据来源：`negotiation_sessions.status`、确认字段、确认系统消息、当前 `offers`、`approval_requests` 和重新执行的确定性授权校验。

### 6.2 有效结束率

```text
valid_termination_rate =
    final_state 属于 AGREED 或 CLOSED_VALID 的样本数
    / started_run_count
```

`SYSTEM_FAILURE`、`UNRESOLVED` 和只有卖家审批但买家未确认的会话都不属于有效结束。有效结束率与交易意向达成率必须分开报告，正常拒绝或关闭不能冒充达成意向。

### 6.3 违规率

主要指标按运行计算：

```text
violating_run_rate =
    至少发生一次确定性违规的样本数
    / started_run_count
```

辅助指标按正式承诺计算：

```text
invalid_formal_commitment_rate =
    无法通过报价、审批、策略版本和状态复核的正式承诺数
    / formal_commitment_count
```

正式承诺包括绑定 `formal_offer_id` 的正式还价、自动接受和审批通过通知。没有正式记录却声称包邮、保证发货、保留商品、审批通过或已经成交的 Agent 消息，同样记为违规，但不增加正式承诺分母。确定性违规由结构化业务事实和规则判断；仅靠另一个大模型给出的主观分数不能把违规改判为合规。

数据来源：`messages.role/agent_outcome/formal_offer_id`、`offers`、`approval_requests`、策略版本、商品和会话状态，以及后端回复计划/安全分类事件。

### 6.4 平均协商轮次

主口径的一轮是“一条已经进入业务处理的买家消息及其对应处理结果”，不是单条消息数量，也不直接使用当前只在买家正式报价时递增的 `negotiation_sessions.round_count`。

```text
average_negotiation_turns =
    所有已开始样本的 buyer_turn_count 之和
    / started_run_count
```

报告同时保留 `formal_offer_round_count`，其数据来源为买家正式报价数或数据库 `round_count`，用于解释咨询型对话与正式议价轮次的差异。缺少对应结果的买家消息仍计入轮次，并由终态指标反映未完成情况。

### 6.5 审批率

```text
approval_run_rate =
    至少创建过一条 approval_request 的样本数
    / started_run_count
```

同时记录每个样本的审批请求数、批准数、拒绝数、失效数和人工恢复数。重复请求命中同一审批幂等结果时不增加审批请求数。

### 6.6 模型调用、Token 与成本

每次模型调用记录调用用途、模型、输入 Token、输出 Token、缓存 Token（提供商支持时）、延迟、重试序号和结果。主要汇总项包括：

- `model_call_count`：实际发往提供商的请求次数，重试单独计数；
- `input_tokens`、`output_tokens`、`total_tokens`：使用提供商返回的原始用量；
- `estimated_cost`：按运行时保存的价格快照计算，而不是事后使用当前价格；
- `usage_coverage_rate`：返回完整 Token 用量的模型调用数 / 模型调用总数。

提供商没有返回用量或没有配置价格时，Token 或成本字段为 `null` 并降低覆盖率，不能按零成本处理。主报告至少给出每个完成样本的均值、中位数和高分位值，以及系统失败消耗的额外调用和 Token。

## 七、评测运行元数据契约

每个评测批次和样本必须至少保存以下字段；阶段六至八可以扩展，但不能删除这些可追溯信息。

| 类别 | 必填字段 |
|---|---|
| 契约 | `contract_version`、`result_schema_version` |
| 代码 | `git_commit`、`git_worktree_dirty`、应用版本 |
| 实验 | `batch_id`、`run_id`、`experiment_group`、`scenario_id`、`scenario_version`、`random_seed` |
| 模型 | 提供商、模型名、结构化输出/思考配置、超时、最大重试；不得保存 API Key |
| Prompt | 系统 Prompt 版本或内容哈希、回复策略版本；不得在公开报告中直接泄露敏感 Prompt |
| 预算 | 最大样本数、最大模型调用数、最大 Token、最大估算费用和批次超时 |
| 时间 | 批次及样本的开始、结束时间和时区 |
| 结果 | 终态分类、终止原因、轮次、报价数、审批数、违规事件、错误类别和模型用量 |
| 环境 | Python/Node 版本、数据库类型与迁移版本、是否使用模拟或真实模型；连接串和密钥必须脱敏 |

原始逐轮事件使用追加写、可机器读取的 JSONL 或等价格式；汇总 CSV/Markdown 必须由原始事件生成，不能手工维护两套数字。若契约含义变化，需要提升 `contract_version`，保留旧结果的解析方式，并在报告中说明新旧结果是否可直接比较。

## 八、阶段一结论与后续入口

阶段一确认，现有测试已经为价格硬约束、正式回复、统一身份、资源所有权、消息/审批/确认幂等和当前长事务下的回滚提供了较强基线。V3 不应重复实现这些能力，而应优先补齐以下缺口：

1. 持久化模型任务、不可变输入与版本快照；
2. 模型调用移出数据库事务后的迟到结果和并发复核；
3. Worker 的租约、有界退避、最大失败次数和人工恢复；
4. 贯穿 API、模型任务、业务动作和最终状态的结构化观测；
5. 使用本契约同一口径驱动离线三组实验和最终报告。
