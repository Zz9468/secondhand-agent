继承的旧 Worker 仍不处理新图会话。

## 卖家操作与买家效果

1. 买家提交审批区的有效报价，聊天得到等待说明。主协商图结束本轮，审批线程
   `approval:{approval_id}:v1` 独立等待，买家仍可询问商品或审批进展。
2. 卖家进入“报价审批”，查看报价、审批响应截止、决定、效力和买家通知状态。
   同意只保存授权；审批 Worker 复核后才接受报价并发布可确认卡片。
   拒绝接口原子完成拒绝、退出等待及通知义务，审批图只负责其后的通知与结清。
3. 新图的批准/拒绝接口仍为 `POST /api/seller/approvals/{id}/approve|reject`，
   请求包含 `request_id`、可选 `comment` 和当前 `expected_effect_revision`。
   前端已经传递版本，重试保持同一载荷；修改意见会生成新请求键。
   同键不同载荷返回 409，跨账号操作返回 404。旧会话不要求新增版本字段。
4. `status` 记录卖家决定，`effect_status` 为 NOT_APPLIED / APPLIED / INVALIDATED。
   `effect_revision` 随公开效力变化递增；`notification_status` 独立表示通知进度。
   批准后撤回或改价会保留 APPROVED、审批时间和意见，同时记录失效原因与替代报价。
5. 买家最终确认仍须使用发送前已展示的具体方案。批准未应用时不能确认；应用后、最终确认前
   可以改价或撤回；AGREED 后拒绝修改。Agent 还价被新方案替代时记为 REJECTED。

审批响应截止一般为请求后 30 分钟，并受报价与成本有效期限制。截止前保存的卖家批准可以稍后应用，
前提是原报价和所有依据仍有效；批准、重试及刷新卡片均不会延长报价。
新图的审批截止、审批时间和失效时间通过 API 明确携带 UTC 时区，页面按浏览器时区显示。

## 对账与故障边界

- Outbox 事件是唤醒引用；恢复只传 `event_id`，应用节点重新读取真实决定、报价和依据。
  早于 interrupt 的决定、重复事件以及较晚到达的旧决定都会被结清。
- 自动对账按最近检查时间轮转当前未确认报价，处理响应到期、报价/成本到期、事实和策略失效。
  普通咨询不增加业务版本、不取消审批。旧审批只影响其关联报价，不把新等待状态改回 ACTIVE。
- 每个审批效力版本的通知来源为 `approval:{id}:result:{revision}`。
  正常图和独立通知共享发布事务，历史接受结果不会再开放旧确认凭据。
- 图持有独立 PostgreSQL 线程锁和 MySQL 执行租约。checkpoint 缺失或版本不符保留恢复需求；
  不从空状态重新应用有执行证据的旧审批。发布失败保留独立通知义务，三次失败后进入人工恢复状态。
  恢复管理界面和生产监督器的完整交付分别保留给 P4/P6，不应手工改 checkpoint 绕过检查。

## 复验

以下命令在 `backend/` 执行。脚本为每次运行创建随机临时数据库，并在结束时清理：

```powershell
..\.venv\Scripts\python.exe -m scripts.run_graph_tests tests/graph/test_approval_lifecycle.py `
  tests/graph/test_graph_boundaries.py --junitxml=../artifacts/p3/recheck-approval.xml
..\.venv\Scripts\python.exe -m scripts.run_graph_tests tests/graph tests/p0 `
  --junitxml=../artifacts/p3/recheck-protocol.xml
..\.venv\Scripts\python.exe -m scripts.run_isolated_mysql_tests tests/unit tests/integration `
  tests/test_health.py tests/test_model_contract.py --junitxml=../artifacts/p3/recheck-legacy.xml
..\.venv\Scripts\python.exe -m ruff check app evaluation tests scripts migrations
..\.venv\Scripts\python.exe -m pip check
```

不要同时运行两次 `run_graph_tests` 或真实模型图脚本，它们复用 P0 的临时角色初始化流程。
旧业务 MySQL 回归使用另一套临时库，可以独立执行。前端用 `npm run build` 验证类型和构建。

真实模型开发验收（用户已授权模型调用无上限；每输入的运行预算仍保留）：

```powershell
..\.venv\Scripts\python.exe -m scripts.run_p3_live_tests --allow-real-model `
  --output ../artifacts/p3/recheck-live.json --junitxml=../artifacts/p3/recheck-live.xml
```

此命令同时运行 P2 语义回归和 P3 真实模型链路，使用现有配置，保存所有调用及失败证据，
拒绝覆盖已有报告。新输入使用 `p3-intents-v1`；旧冻结输入仍使用其原提示词。
它是开发回归，不是 P5 的独立风险保留集，也不会启动常驻生产服务。
