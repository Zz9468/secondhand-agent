# P1 运行与复验

本阶段复用 [P0 隔离环境](P0_运行与复验.md)。命令只在新仓库
`E:\code\agent\SecondHand_Agent` 执行；账号、端口、数据库及秘密配置均沿用该独立环境。

## 测试

在 `backend/` 执行：

```powershell
# 为本次运行创建随机 MySQL/PostgreSQL 临时库，执行迁移升/降/升及 P1 专项，最后清理。
..\.venv\Scripts\python.exe -m scripts.run_graph_tests

# 同一次隔离环境运行 P1 与 P0（包含跨进程、锁、监督器、网络分区及本地追踪故障注入）。
..\.venv\Scripts\python.exe -m scripts.run_graph_tests tests/graph tests/p0 `
  --junitxml=../artifacts/p1/recheck-protocol.xml

# 旧业务全量真实 MySQL 回归；同样只使用本次创建的隔离数据库。
..\.venv\Scripts\python.exe -m scripts.run_isolated_mysql_tests `
  tests/unit tests/integration tests/test_health.py tests/test_model_contract.py `
  --junitxml=../artifacts/p1/recheck-legacy.xml

..\.venv\Scripts\python.exe -m ruff check app evaluation tests scripts migrations
..\.venv\Scripts\python.exe -m pip check
```

未配置真实数据库时专项测试会跳过，不算验收通过。`run_graph_tests` 复用 P0 的临时库管理脚本，
所以临时库名仍是 `p0_test_<随机后缀>`；不得把名称误解为仍在使用 `p0_*` 业务夹具。
P1 通过 Alembic 创建并操作正式 ORM 表。所有测试模型均为本地回调，没有真实模型费用。

## 新开发库与 Worker

在独立环境完成 saver setup 后，从 `backend/` 执行：

```powershell
..\.venv\Scripts\python.exe -m alembic upgrade head
..\.venv\Scripts\python.exe -m alembic check

# 新图单批调度；空库应返回 completed/notified/busy/failed 全 0。
..\.venv\Scripts\python.exe -m app.workers.graph_worker --once

# 需要持续处理已入库的内部图输入时运行；每秒扫描一次，Ctrl+C 退出。
..\.venv\Scripts\python.exe -m app.workers.graph_worker --batch-size 20
```

Worker 读取 `DATABASE_URL` 和 `CHECKPOINT_DATABASE_URL`；MySQL 连接/读/写超时为 3/5/5 秒，
事务内锁等待 2 秒，SELECT 服务端期限 5 秒；PG 专用锁连接不自动重连。每次图领取租约 30 秒，
失败保留 FIFO、最多 3 次自动尝试；恢复证据冲突或次数耗尽需要明确恢复处置。通知独立租约
15 秒，最多 3 次自动发布尝试，耗尽保留 `MANUAL_REQUIRED` 义务。P1 图无模型慢调用；P4/P6
仍需接入长调用心跳、完整活动时间预算和生产监督器，不能把单个 CLI 进程等同于完整可用性部署。

P1 临时业务测试覆盖 `SubmitOfferAndResolve`、`ReplaceOfferAndResolve`、确认、撤回、关闭与查询。
其 Python 入口为 `InputQueue.enroll/enqueue` 和 `GraphRunner.run`；只允许将空会话绑定到图。
测试示例见 `backend/tests/graph/test_business.py`、`test_display_queue.py`，不提供可从 HTTP 绕过
语义校验的固定报价测试接口。

## 状态与恢复

买家登录后可查询 `GET /api/negotiations/{session_id}/runs/{run_id}`。API 单独报告：

- `task_status` / `blocked_by_input_seq`：执行与顺序屏障。
- `business_status` / `business_outcome`：是否已提交，以及实际业务结果。
- `notification_status` / `public_message_id`：结果是否已发布。
- `recovery_required` / `public_error_category`：checkpoint 异常或结果投递延迟。

不能因 `RETRY_WAIT` 或通知失败把 `COMMITTED` 解释为业务未发生。重新运行原 run 只会恢复对应
执行位置、读取回执或返回历史结果。确认凭据不能从“当前最近报价”补入旧输入。原图必须 END
且唯一消息存在才能推进游标；独立通知只能履行消息义务。

checkpoint 丢失/版本不符时不要删除输入、重建空线程或手工推进游标。保留数据库、回执、调用
账本及官方 checkpoint 作为恢复证据；不使用旧卖家恢复接口改写新图任务。当前不提供绕过恢复
核验的管理员按钮。正式卖家恢复入口按 P4 实施。

迁移回退只在隔离测试中验证。已产生新图记录的开发环境回退运行时应保留新增表和证据，避免
将新版会话交给旧 Runtime。终态归档及生产清理策略留待 P6。
