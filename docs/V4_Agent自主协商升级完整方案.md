# V4 Agent 自主协商升级完整方案

本次升级围绕自主工具循环、协商记忆和动态买家评测展开。完整 Agent 消息流保存从买家输入到最终回复的执行记录，现有 messages 表保存其中的公开对话投影。每次模型调用从完整消息流构建上下文，并在发送前检查 Token 预算、压缩历史和验证消息协议。

主协商 Agent 决定需要哪些信息、调用什么工具、如何根据反馈调整方案，以及何时澄清或结束。已有业务服务继续负责工具执行和正式交易授权；已有模型任务负责租约、重试和恢复。第一批沿用 Python 3.11、LangChain 和 MySQL，不引入多 Agent、强化学习、支付或库存锁定。

日期：2026 年 10 月 6 日。

## 1 升级目标与现有实现

| 项目 | 现有 V3 | V4 目标 |
| --- | --- | --- |
| 决策过程 | 程序准备上下文，模型生成候选决策，程序执行对应工具 | 模型自主选择工具，读取结果，继续决策或结束 |
| 历史来源 | messages 最近 20 条记录 | 完整 Agent 消息流，按预算选择或压缩 |
| 消息保存 | 买家消息、最终回复、审批通知 | 公开对话与内部工具轨迹完整关联 |
| 记忆 | 最近对话、报价和业务状态 | 明确诉求、未解决问题、已尝试方案与当前计划 |
| 系统提示词 | prompts.py 常量，由模型适配层注入 | 版本化配置，运行冻结，实际请求可复现 |
| 恢复 | 不可变任务输入、租约、整轮重试、最终版本复核 | 保留既有机制，增加步骤恢复与工具结果对账 |
| 评测 | 固定脚本买家、A/B/C 对照、安全门禁 | 固定回归集加动态买家，独立评估上下文、工具循环与记忆 |

现有代码中的关键事实：

- [ChatService](../backend/app/services/chat_service.py) 的 _recent_history 取本会话最近 20 条历史；历史查询发生在本轮买家消息入库之前，本轮输入随后单独追加。
- [LangChainDecisionProvider](../backend/app/agent/decision_provider.py) 使用 tools=[] 和 ProviderStrategy 获取结构化决策。当前 ConversationMessage 只表达 role 与字符串 content。
- [SellerAgent](../backend/app/agent/seller_agent.py) 固定要求六个业务工具，由代码读取上下文和应用决策；还价提交失败后返回安全失败，没有工具结果驱动的重新规划。
- [Message](../backend/app/db/models/message.py) 保存正式发送或接收的会话消息；当前消息接口直接返回这些记录，不能直接混入内部工具轨迹。
- [ModelExecutionTask](../backend/app/db/models/model_task.py) 已保存输入、输入哈希、版本、租约、用量和最终结果，但尚未保存完整的逐步模型消息。
- [SimulatedBuyer](../backend/evaluation/buyer.py) 回放场景中的 turns；[评测适配器](../backend/evaluation/adapters.py) 按固定目标判断接受，部分回复由评测安全模板生成。

上述 V4 目标是待实施设计，现有 V3 行为作为兼容基线保留。

## 2 核心设计决定

1. 完整 Agent 消息流是对话与工具历史的原始来源。只追加新增消息，不反复保存整个请求数组到同一条消息序列。
2. messages 是公开对话投影。买家输入、实际发送的回复和审批通知都必须能够关联到完整消息流。
3. 原始消息流保持完整。上下文压缩产生摘要和新的输入视图，不覆盖原始消息。
4. 每次模型调用前执行上下文检查，包括同一轮 ReAct 内的后续调用。
5. 系统提示词版本由运行冻结。历史 SYSTEM 配置记录不作为旧指令全部重放。
6. 协商记忆记录语义状态并保留来源；正式报价、审批和商品状态以业务数据库为准。
7. Agent 自主选择受约束工具。只读工具支持多步探索；成功的正式业务变更结束本轮，正式回复由已提交事实生成。
8. 第一批使用一个主协商 Agent。专家协作与跨会话经验学习在完成本方案的消融评测后再决定。
9. 运行恢复不依赖模型重新猜测已经做过什么。已完成步骤通过持久化结果对账，写工具具有稳定的执行标识。
10. 一个会话同一时间仍只有一个活动聊天任务；审批通知等外部变化继续触发版本复核。

## 3 总体架构

~~~mermaid
flowchart TB
    Buyer[买家输入] --> Chat[ChatService]
    Chat --> Task[持久化模型任务]
    Task --> Runtime[SellerAgentRuntime]
    Runtime --> Builder[ContextBuilder]
    Stream[完整 Agent 消息流] --> Builder
    State[摘要与协商记忆] --> Builder
    Prompt[版本化系统提示词] --> Builder
    Builder --> Budget[Token 检查与压缩]
    Budget --> Model[LangChain 模型适配]
    Model --> Runtime
    Runtime --> Gateway[受约束 ToolGateway]
    Gateway --> Services[已有业务 Service]
    Gateway --> Stream
    Runtime --> Stream
    Runtime --> Memory[MemoryUpdater]
    Memory --> State
    Stream --> Projection[messages 公开投影]
    Projection --> UI[现有聊天界面]
    Worker[现有 ModelTaskWorker] --> Task
    Eval[动态评测环境] --> Runtime
~~~ 

LangChain 负责模型消息、工具描述和模型适配；SellerAgentRuntime 明确驱动有界循环，统一步骤持久化、预算和终结动作。其运行方式遵循“模型调用工具并根据结果继续”的 Agent 循环，[LangChain 官方 Agents 文档](https://docs.langchain.com/oss/python/langchain/agents)提供了对应机制。

第一批不再额外建立一个独立维护历史的 LangGraph checkpointer。运行状态统一由本项目消息流和模型任务恢复机制管理。后续采用 LangGraph 驱动执行时，应通过适配层使用同一持久化来源，并向已恢复状态提交增量消息，避免两套权威历史或重复注入全量对话。

## 4 消息流与公开会话

### 4.1 消息分类

完整消息流需要同时区分角色、用途和可见性。

| 角色 | 用途 kind | 内容 | 可见性 |
| --- | --- | --- | --- |
| USER | BUYER_INPUT | 买家实际发送的消息及请求关联 | PUBLIC |
| ASSISTANT | TOOL_CALL | 原生工具调用列表，或已校验的结构化结束封装；后者标识来源并保留实际模型输出 | INTERNAL |
| TOOL | TOOL_RESULT | 对应工具结果或可供模型处理的错误 | INTERNAL |
| ASSISTANT | MODEL_CANDIDATE | 候选回复或结构化结束计划 | INTERNAL |
| ASSISTANT | PUBLIC_REPLY | 实际发送给买家的最终回复 | PUBLIC |
| ASSISTANT | APPROVAL_NOTIFICATION | 审批处理后实际发送的业务通知 | PUBLIC |
| SYSTEM | RUN_CONFIG | 提示词、工具集和模型配置的冻结引用 | INTERNAL |
| SYSTEM | CONTEXT_ARTIFACT | 摘要或协商记忆的版本化快照 | INTERNAL |
| SYSTEM | RUNTIME_EVENT | 路由、取消、失效、恢复等执行事件 | INTERNAL |

这些用途中，只有明确选定的模型消息参与历史重放。RUN_CONFIG、CONTEXT_ARTIFACT 和 RUNTIME_EVENT 作为运行记录或引用处理，不直接堆叠成模型系统指令。

“完整”包括可用于还原执行的输入、模型输出、工具调用、工具结果、上下文快照和最终回复。模型服务不返回的私有思考过程不属于本方案需要自行生成的记录。错误堆栈、HTTP 调试和性能指标继续进入可观测系统，不自动进入模型上下文。

### 4.2 工具消息协议

~~~text
USER
  买家实际输入

ASSISTANT TOOL_CALL
  tool_calls:
    - id: call_01
      name: evaluate_offer
      args: 候选交易条件

TOOL TOOL_RESULT
  tool_call_id: call_01
  name: evaluate_offer
  content: 可执行权限与条件有效性

ASSISTANT
  继续调用工具，或形成结束计划
~~~

调用与结果必须按 ID 对应。一个 ASSISTANT 消息可以包含多个工具调用，第一批按返回列表顺序串行执行。一个批次最多包含一个终结动作，且必须位于最后；不符合要求时不执行该批次，为每个调用返回明确的协议错误，再在预算内重新决策。不能执行第一个写动作后丢弃其余调用，留下没有结果的工具消息。

提供商支持时关闭并行工具调用。即使关闭，仍由 Runtime 验证返回的完整调用列表，不能把模型参数设置当作执行保证。

必须保留原生消息的结构化载荷，不能把工具结果改成普通 AI 文本。模型可见结果与详细附属数据可以分别保存，[LangChain Messages 文档](https://docs.langchain.com/oss/python/langchain/messages)说明了 tool_call_id 关联和 artifact 数据的区别。摘要和裁剪以完整工具交互为边界，不能截断调用结果配对。

### 4.3 messages 投影

messages 继续保持当前 API 字段与 BUYER、AGENT、SYSTEM 角色契约。新增可为空且唯一的 source_agent_message_id，指向原始公开消息。

messages 中的 SYSTEM 业务通知角色与模型的系统指令角色不同。审批通知在原始流中使用业务通知用途，构建模型历史时作为可追溯业务信息处理，不能把旧 messages.SYSTEM 自动转换成高优先级 SystemMessage。

- 新买家输入在同一短事务中写入完整消息流和 messages。
- 最终回复在正式业务结果提交的同一短事务中写入完整消息流和 messages。
- 审批通知也通过同一个公开消息写入入口投影。
- INTERNAL 消息不投影到买家聊天接口。
- PUBLIC_REPLY 必须是实际发送的文本，不能用尚未校验的模型候选替代。

投影不是第二份独立编辑的历史。补偿或重建根据公开原始记录和稳定请求标识完成；已有 messages 的请求幂等约束继续有效。

## 5 持久化模型

新增三张核心表，扩展两张现有表。提示词第一批放在版本化源码文件中，运行保存版本、哈希与实际内容，不另建提示词管理平台。

### 5.1 agent_messages

| 字段 | 含义 |
| --- | --- |
| id | 全局主键 |
| session_id | 协商会话 |
| stream_seq | 本会话内递增的消息序号 |
| model_task_id | 所属运行，可为空的历史导入记录或外部通知 |
| run_branch_id | 当前执行分支，区分重规划和已放弃分支 |
| lease_attempt | 生成记录时的租约尝试号 |
| logical_step_id | 稳定步骤标识，恢复后沿用 |
| role | USER、ASSISTANT、TOOL、SYSTEM |
| kind | 第 4 节定义的用途 |
| visibility | PUBLIC 或 INTERNAL |
| event_key | 稳定幂等标识 |
| tool_call_id | 工具结果的关联 ID，可为空 |
| payload | 原生消息内容、工具调用列表或版本化执行载荷 JSON |
| schema_version | 消息载荷版本 |
| created_at | 保存时间 |

约束与索引：

- UNIQUE(session_id, stream_seq)。
- UNIQUE(session_id, event_key)。
- INDEX(model_task_id, run_branch_id, logical_step_id)。
- INDEX(session_id, visibility, stream_seq)。

stream_seq 由会话上下文行上的计数器在短事务中分配，分配与消息追加一起提交。新增内部消息不递增业务 negotiation.version，避免工具查询日志使自己的运行被误判为迟到结果。

原始消息内容不回写修改。取消、失效或分支放弃通过新事件和任务检查点表达；上下文选择器过滤对应分支。

### 5.2 agent_session_contexts

每个会话一行，保存当前上下文缓存：

| 字段 | 含义 |
| --- | --- |
| session_id | 主键 |
| next_stream_seq | 下一条原始记录序号 |
| context_version | 摘要与记忆缓存版本 |
| summary_artifact_id | 当前摘要原始快照引用 |
| summary_covered_through_seq | 摘要已经覆盖的完整交互边界 |
| summary_text | 当前历史摘要 |
| memory_artifact_id | 当前协商记忆原始快照引用 |
| memory_covered_through_seq | 记忆已经处理到的来源边界 |
| memory_json | 结构化协商记忆 |
| memory_schema_version | 记忆结构版本 |
| legacy_backfill_status | 历史导入进度 |
| updated_at | 更新时间 |

旧摘要和旧记忆作为 CONTEXT_ARTIFACT 记录保留，使运行引用的版本可还原。当前缓存行只保存最新版本，不承担原始历史的唯一保存职责。

会话摘要只发布覆盖已结束、已选择分支的历史前缀。当前运行压缩自身工具交互时，生成带 run_branch_id 的临时摘要，引用写入 runtime_checkpoint；运行失败或分支放弃后，这份临时摘要不发布到会话缓存。来源清单同时记录序号范围与分支选择，覆盖游标不表示所有内部事件都需要重放。

更新使用预期版本比较。基于某个前缀生成的摘要不能覆盖更晚已发布的摘要；新增买家消息仍保留为未覆盖增量。

### 5.3 agent_call_snapshots

每次应用可追踪的卖家模型请求保存一条记录，覆盖聊天决策、摘要和记忆提取。

| 字段 | 含义 |
| --- | --- |
| id | 请求记录主键 |
| model_task_id | 所属运行或维护任务 |
| run_branch_id | 执行分支 |
| logical_step_id | 所属步骤 |
| call_attempt | 本步骤的提供商尝试号 |
| purpose | REACT、FINALIZE、SUMMARY、MEMORY |
| request_payload | 实际送出的系统消息、工具定义、历史和参数 |
| request_hash | 规范化请求哈希 |
| context_manifest | 提示词、来源序号、摘要、记忆、业务版本与预算信息 |
| response_payload | 返回的原生模型消息，可为空 |
| status | STARTED、SUCCEEDED、FAILED、UNKNOWN |
| usage_json | Token、估算成本和价格快照 |
| started_at 与 completed_at | 耗时信息 |

实际请求保存的是检查与压缩后的输入。运行记录里的 SYSTEM 配置只保存一次，调用快照仍包含每次真正发送的系统提示词。这两种记录分别服务执行追踪与准确复现，不会再次拼接进对话序列。

动态评测沿用同样的调用记录格式，但保存到隔离评测环境和实验产物；BUYER_SIMULATION 使用实验运行标识，不写入生产任务或会话表。

若服务端已处理请求但客户端未取得响应，结果和费用可能未知。保留 UNKNOWN 记录，不声明模型调用恰好一次，也不将未知费用记为零。

### 5.4 扩展 model_execution_tasks

复用现有任务表管理运行，不新增一张语义相同的 agent_runs 表。新增 runtime_kind、runtime_schema_version、runtime_checkpoint JSON、run_budget_json 和累计用量字段或等价结构。

检查点至少保存：

~~~json
{
  "active_branch_id": "branch-1",
  "last_completed_logical_step": 2,
  "pending_tool_calls": [],
  "terminal_action_committed": false,
  "reply_request_id": "existing-reply-key",
  "prompt_version": "seller-react-v1",
  "toolset_version": "seller-tools-v1",
  "input_high_water_seq": 120,
  "last_call_snapshot_id": 30,
  "stop_reason": null
}
~~~

原有 input_snapshot 保持不可变，记录输入、初始历史高水位、选用的记忆、提示词与版本。运行步骤和实际模型请求写入新记录，不能覆盖原始任务快照。

checkpoint 中的 logical_step_id 与租约 attempt_count 不同。Worker 接管是技术尝试增加，已经完成的逻辑步骤不从头编号，也不获得新的预算。

### 5.5 扩展 messages

仅增加 source_agent_message_id 和对应唯一索引。现有内容、请求标识、结果字段和前端响应结构继续使用。

## 6 系统提示词与工具定义

第一批将提示词拆为版本化资源，例如 app/agent/prompts/seller_react_v1.md、history_summary_v1.md 和 negotiation_memory_v1.md。这里是拟议文件结构，现有 prompts.py 可在过渡期通过加载适配继续工作。

主提示词覆盖卖家协商目标、工具用途、信息不足时的澄清、正式动作的条件、结束要求以及预算耗尽时的处理。它不包含私有最低价或自动接受阈值。

每个运行冻结：

- 提示词正文、版本和 SHA-256。
- 工具名称、描述、参数 Schema 与工具集版本。
- 模型提供商、名称、关键参数和已验证能力。
- 上下文策略版本及运行预算。

每次模型调用只注入本次生效的固定指令和当前数据。旧运行中的 SYSTEM 配置记录用于审计，不作为多份历史指令重放。摘要、买家文本和商品描述应被明确标识为数据，不能通过压缩升级成系统指令。

同一任务重试或恢复沿用冻结版本。新任务可以使用新版提示词，摘要继续描述对话事实，不能携带旧提示词的指令要求。

## 7 上下文构建与长度控制

### 7.1 组件职责

ContextBuilder 负责将持久化消息和运行状态转成一次模型输入。TokenBudgetManager 负责估算完整输入，ContextCompressor 负责超预算时生成可追溯摘要，MessageProtocolValidator 负责工具调用配对和消息结构。

已有 role/content 历史对象应被结构化 AgentMessageRecord 或等价 Pydantic 模型替代。转换器分别恢复 HumanMessage、AIMessage、ToolMessage 和选定的 SystemMessage，不能沿用“非 BUYER 都转为 AIMessage”的逻辑。

### 7.2 构建顺序

每次模型调用：

1. 读取当前运行检查点，确认租约和可用预算。
2. 使用本次固定提示词与工具 Schema。
3. 读取最新公开商品事实和当前正式协商状态；这些事实不能仅从历史记忆推断。
4. 读取本运行选择的摘要和协商记忆版本。
5. 读取摘要覆盖位置之后、input_high_water_seq 以内的可用历史，包括本轮买家输入；排除过期配置、放弃分支和非模型事件。
6. 加入高水位之后本运行有效分支的模型消息和工具交互，按来源序号去重，保留完整调用结果配对。
7. 估算整个请求的 Token 数，必要时压缩完整历史前缀。
8. 验证协议、重复消息和预算，保存实际调用快照。
9. 调用模型；仅将新返回的消息追加到原始流。

当前买家消息已经属于完整流，只注入一次。新运行历史边界由 input_high_water_seq 冻结；正在进行的本运行步骤可以继续增量进入上下文。

若本轮发生审批、商品或策略变化，原始事件继续记录，但旧运行在动作执行前会被版本复核阻断。重新规划使用新分支和新业务事实，不能悄悄改写旧输入。

### 7.3 Token 预算

~~~text
C = 已确认的模型上下文上限
O = 输出预留
H = 估算误差与协议开销预留
A = 应用输入预算

B = min(A, C - O - H)
N = 固定指令 + 工具定义 + 当前事实 + 记忆 + 摘要 + 消息 的估算 Token
~~~

N 必须不超过 B。第一轮还需要预留工具结果增长空间 G；后续每个步骤重新计算 N，不依赖初始检查。

计数优先使用适用于当前模型的实现，并通过提供商返回的实际用量校准。计数器覆盖工具 Schema、消息封装和 JSON 内容；缺少精确计数时使用保守估算及配置的余量。模型上下文上限必须来自已核实能力或显式配置，不能凭模型名称猜测。

建议的初始实验配置如下，属于可调应用参数，不是模型规格或已验证最优值：

| 配置 | 初值 |
| --- | --- |
| APP_INPUT_TOKEN_BUDGET | 16000 |
| MODEL_OUTPUT_TOKEN_RESERVE | 1024 |
| CONTEXT_TOKEN_SAFETY_MARGIN | 1024 |
| INITIAL_TOOL_GROWTH_RESERVE | 2048 |
| COMPRESSION_TRIGGER_RATIO | 0.8 |
| COMPRESSION_TARGET_RATIO | 0.6 |
| TOOL_RESULT_TOKEN_LIMIT | 1500 |
| AGENT_MAX_MODEL_STEPS | 6 |
| AGENT_MAX_TOTAL_MODEL_CALLS | 10，含提供商尝试、修复、摘要与记忆调用 |
| AGENT_MAX_MAINTENANCE_CALLS | 2，受总调用预算约束 |
| AGENT_MAX_TOOL_CALLS | 8 |
| AGENT_MAX_WALL_SECONDS | 120 |

预算还受实际模型窗口和已有 Worker 租约配置约束。运行还应配置累计 Token 上限；已核实价格时增加估算费用上限，发起下一次请求前预留其最大用量。未知服务端用量通过调用数和预留量保守计入预算，不能因响应缺失无限重试。

大工具结果在写入消息前按工具契约提取模型可见字段；完整附属载荷保留为 artifact。身份、价格与正式报价不能由通用摘要随意裁切。

### 7.4 压缩策略

短会话采用完整历史。超过触发预算后，将较早的完整交互前缀合并到已存在摘要；近期交互优先保留原文，保留数量由 Token 预算决定。

摘要包含商品咨询要点、买家明确诉求、尝试过的条件、有效澄清与未解决问题，并附来源覆盖范围。正式金额、报价编号、审批事实必须可与业务数据核对；未知信息保持未知。

固定提示词、当前买家输入、正在等待结果的调用和当前生效业务事实保留。已完成工具交互可以整体进入摘要，不能仅保留 call 或 result 的一半。

摘要与输入中出现的重叠来源只保留一份。反复压缩时保留覆盖游标；相关旧细节可以通过受约束历史查询工具重新读取。[LangChain 短期记忆文档](https://docs.langchain.com/oss/python/langchain/short-term-memory)提供了摘要与历史裁剪机制。

“基于完整流”不要求每次都把数据库中的全部原文读入内存。短会话可以全量读取；长会话直接读取已验证摘要与覆盖位置后的增量，并保留按来源查询旧原文的能力。进入模型的逻辑历史仍来自完整流。

压缩失败时优先使用已有摘要，并在预算内保留近期完整交互。仍无法容纳固定输入或当前步骤时停止模型调用并返回可恢复的明确结果，不截断工具协议。原始记录完整保留。

摘要模型调用发生在数据库事务之外，其用量单独记录并计入总成本。

## 8 协商记忆

### 8.1 第一批记忆范围

仅维护当前商品、当前买家、当前协商会话的记忆，不将不同买家的预算或对话合并。跨会话经验学习暂不启用。

~~~json
{
  "schema_version": 1,
  "buyer_statements": [
    {
      "field": "stated_budget",
      "value": "2800.00",
      "source_seqs": [12],
      "status": "ACTIVE"
    },
    {
      "field": "delivery_preference",
      "value": "pickup",
      "source_seqs": [18],
      "status": "ACTIVE"
    }
  ],
  "open_questions": [
    {"question": "面交地点", "source_seqs": [18], "status": "OPEN"}
  ],
  "attempted_options": [
    {
      "description": "原包邮条件",
      "result": "NOT_AUTHORIZED",
      "source_seqs": [14, 15]
    }
  ],

~~~

stated_budget 是买家说出的预算，不能等同其真实最高支付能力。假设不会成为商品事实或执行权限。有效正式报价从业务数据单独注入，不把记忆里的描述当成当前报价。

### 8.2 更新规则

- 初始记忆为空；根据新输入和已经完成的工具结果产生 MemoryDelta。
- 每项新增或替代内容引用存在且属于本会话的来源序号。
- 买家改变条件时，原条目标记为被替代，保留可追溯来源。
- 已回答问题标记为已解决；不把模型自己的猜测写成买家陈述。
- 正式业务动作完成后，根据已提交结果补充结果事实。
- 记忆文本长度受限，过长时合并旧尝试，保留当前诉求和未解决问题。
- 记忆写入失败不撤销已完成的报价与公开回复；标记覆盖游标落后，之后从新来源补齐。

第一批优先从最终模型结果中取得结构化 MemoryDelta，并校验来源和字段。必要的独立提取调用使用单独预算，不在数据库写事务内调用模型。

运行开始时冻结所用记忆；本轮自己的增量进入运行状态，结束后发布到会话缓存。外部维护更新采用版本比较，不能覆盖较新的记忆。

## 9 自主工具循环

### 9.1 工具分类

| 工具 | 类型 | V4 行为 |
| --- | --- | --- |
| get_product_info | 查询 | 复用现有商品事实查询 |
| get_negotiation_state | 查询 | 读取当前正式状态和非敏感策略 |
| evaluate_offer | 查询与评估 | 返回权限、条件有效性和可处理错误，不返回私有阈值 |
| search_conversation_history | 新增查询 | 按本会话检索原始对话或工具交互，返回来源与有界结果 |
| submit_counter_offer | 终结写动作 | 校验、提交、生成正式回复，成功后结束 |
| accept_offer | 终结写动作 | 只接受本轮授权的正式买家报价，成功后结束 |
| request_approval | 终结写动作 | 只申请本轮正式报价审批，成功后结束 |
| finish_turn | 新增运行控制 | 提交咨询、澄清或拒绝的结构化结束计划 |

ToolGateway 继续由后端绑定 session_id、buyer_id、当前报价和任务身份。模型参数不允许选择任意账号、会话或任务。

第一批不新增猜测运费、保证发货时间或预订商品的能力。缺少可验证数据时由 Agent 澄清；后续增加运费或发货工具时再定义可靠数据来源与授权契约。

### 9.2 模型交互方式

探索阶段使用当前提供商支持的原生工具调用，允许模型自动选择工具。finish_turn 的参数提供结构化结束契约，例如 dialogue_acts、candidate_reply、stop_reason 和 MemoryDelta。

不假定当前的 ProviderStrategy 与原生工具循环可以不经验证直接共用。先验证千问的工具调用、结果回传和多步能力；若最终 JSON Schema 不能与工具调用同时工作，工具探索与最终结构化输出分两次请求，后一请求也计入步骤预算。不得依赖当前代码已注明不兼容的强制 ToolStrategy。

对模型只输出文本且未调用 finish_turn 的情况，进入有预算的结束处理。新任务的 structured-finish-v2 策略先指定结束工具；提供商仍返回纯文本时，使用独立的原生 JSON Schema 请求生成咨询或拒绝计划。最后一个模型步骤也保留给该结束请求，防止探索耗尽全部步骤。所有请求均计入原有调用、Token、费用和时间上限，不提高预算；无合法结果时仍安全停止。不能把未校验文本直接作为正式承诺。

finish_turn 的对外 Schema 只允许 INQUIRY 或 REJECT，不提供接受、还价、审批字段。JSON 结束请求不绑定业务工具，后端校验决策与非写动作限制后生成标明 STRUCTURED_FINISH 来源的内部执行封装。实际 JSON 输出和请求保留在原始流及调用快照中，不能伪装成提供商的原生工具响应。已有任务继续使用创建时冻结的结束策略。

### 9.3 循环流程

~~~text
接收消息并创建运行
  -> 领取租约
  -> 构建上下文并检查预算
  -> 保存模型请求快照
  -> 调用模型并保存新增输出
  -> 有查询工具：
       校验参数 -> 执行 -> 保存 ToolMessage -> 返回构建上下文
  -> 有终结写工具：
       复核租约、业务版本和权限 -> 提交动作与公开回复 -> 结束
  -> 有 finish_turn：
       校验咨询/澄清/拒绝计划 -> 保存公开回复 -> 结束
  -> 达到预算：
       明确澄清、已有事实回复或可恢复失败 -> 结束
~~~

成功终结写动作的结果足以生成正式回复，第一批不在正式提交之后继续用模型自由改写承诺。查询错误或被拒绝的候选通过 ToolMessage 反馈，Agent 可以换方案；技术失败与业务拒绝分别处理。

### 9.4 保留确定性快速路径

V3 对完整适格正式报价的自动接受与审批路由继续保留。此路径也写入买家原始记录、规则路由事件、带来源的工具执行结果和公开回复，并更新记忆覆盖位置。规则直接发起的执行结果按 RUNTIME_EVENT 保存，不伪造模型 tool_calls，也不生成孤立的 ToolMessage；模型发起的调用才遵循原生调用与结果协议。

Agent 的自主性主要用于咨询、多条件澄清、被禁止报价后的合法替代方案和多轮协商。正式报价路由与全部业务授权规则在各评测版本中相同，避免把授权变化误认为能力提升。

## 10 步骤恢复与一致性

### 10.1 运行与租约

复用既有任务状态、退避和人工恢复。增加租约续期能力或将有界运行时间设置在租约内；每次模型调用、工具执行与步骤保存前验证租约。

业务版本检查继续针对商品、会话、策略和当前报价。内部轨迹序号变化不等于业务版本变化。运行因外部条件失效时，已有轨迹保留，未提交的候选不生效。

### 10.2 写工具执行标识

模型工具调用持久化后，由 Runtime 分配稳定 effect_key，例如 task:任务号:logical_step:步骤号:call:调用号。执行同一已保存调用时沿用该标识，不能在恢复时生成新的写操作。

写动作采用一个短事务：

1. 校验当前租约和预期版本。
2. 按 effect_key 查询是否存在已提交结果。
3. 已存在时返回该结果，不再次执行。
4. 未存在时调用已有事务内业务入口，重新校验权限。
5. 原子保存业务变更、ToolMessage 结果、PUBLIC_REPLY、messages 投影、终结检查点与任务完成状态。

因此“业务已提交但回复记录不存在”的窗口受到同一数据库事务约束。外部网络工具未来需要提供幂等或对账接口，不能把本地事务结论扩展到外部系统。

### 10.3 主要恢复位置

| 中断位置 | 恢复方式 |
| --- | --- |
| 模型请求前 | 使用已保存请求或重新构建同一冻结步骤 |
| 模型请求返回但结果未保存 | 请求结果可能未知，记录尝试后有界重试 |
| 工具调用已保存但尚未执行 | 恢复 pending_tool_calls 后继续 |
| 只读工具结果尚未保存 | 有界重查，记录重新读取时的版本 |
| 写工具事务完成 | 根据 effect_key 和已保存 ToolMessage 返回，不重复写入 |
| 回复已提交但 HTTP 未返回 | 沿用现有请求幂等机制返回 messages 投影 |
| 商品或审批变化 | 将原候选标为失效；需要时以新分支重新规划 |

模型任务预算覆盖步骤、解析修复、提供商重试、恢复尝试及摘要/记忆维护的实际费用，分别统计并汇总。恢复不会重置步骤预算或费用上限。采用运行级预算时，V4 提供商的隐式重试应关闭或被完整观测，避免与任务重试相乘而失控。

## 11 一次协商示例

以下序号是说明流程的示意值。

买家：“2800 包邮，如果便宜一点我也可以自提。”

1. 完整流追加 USER，messages 同步出现买家输入。
2. Runtime 读取当前记忆、商品事实和历史，根据预算决定是否压缩。
3. 模型选择 get_product_info，调用与返回结果进入完整流。
4. 模型选择 evaluate_offer 评估明确且可计算的候选；缺少运费时先形成澄清，不能假设成本。
5. 工具返回不允许的结果后，模型可以结合买家明确的自提选项评估另一候选。
6. 存在合法候选时模型选择 submit_counter_offer；缺少地点等信息时选择 finish_turn 澄清。
7. 公开回复按已验证结果保存，记忆记录“买家可以自提”“地点尚未确认”“原方案未通过评估”及其来源。
8. 动态评测买家读到实际回复，决定回答地点、继续还价、接受或退出。

如果对话没有形成合法正式动作，消息中的金额仍然只是自然语言条件；本轮聊天文字不自动变成正式买家报价。

## 12 动态买家评测

### 12.1 两套评测用途

现有版本化固定脚本、安全门禁和 A/B/C 实验继续运行。新增动态交互评测，用于考察回复是否推动协商、工具选择是否合理、记忆是否有效。

动态买家由目标、行为规则和已发生对话生成下一步输入。可借鉴 [τ-bench 官方项目](https://github.com/sierra-research/tau2-bench) 的用户模拟器、领域工具与任务结果评测设计。引入其思路即可；若运行外部框架，应使用独立环境并固定版本，不直接改变当前 Python 3.11 项目依赖。

### 12.2 买家行为与硬约束

动态买家隐藏配置包含预算上限、配送偏好、初始报价、耐心上限、可调整条件和行为风格。卖家 Agent 只能看到买家实际发送的内容。

建议先覆盖合理买家、持续压价、犹豫、修改条件、关心商品事实和提示注入六类场景。行为风格由模拟器表达，预算与可用动作由环境强制校验。

模拟器输出结构化动作：

~~~text
ASK       咨询或回答澄清
OFFER     提交完整正式报价
CONFIRM   确认环境中的当前有效报价
CLOSE     退出协商
~~~

ASK 中出现数字不自动视为 OFFER；OFFER 需要有效的价格与费用字段。CONFIRM 必须引用真实有效报价，并满足买家硬约束。

不可行的买家输出不会悄悄转换为成功动作。允许一次有界修复，仍失败时标记 BUYER_SIMULATOR_FAILURE，单独报告并计入评测有效性，不归为卖家失败，也不从总体报告中消失。

### 12.3 复用真实 Agent 路径

新增 EvaluationEnvironment 与存储/工具适配器，让生产与评测调用同一 Runtime、ContextBuilder、MemoryUpdater 和 ToolGateway 契约。

动态评测不能继续用 _safe_reply 替代实际回复，否则买家反应与自然度分数不反映真实 Agent。V3 对照也通过生产决策与回复策略的适配路径输出真实回复。

先用小规模内存环境进行大量隔离实验，再用选定场景校验 FastAPI、MySQL 与 Worker 的路径一致性。模拟器从不访问生产买家、卖家或模型任务数据。

### 12.4 实验分组

| 组别 | 上下文 | 工具循环 | 协商记忆 |
| --- | --- | --- | --- |
| G0 | 原 V3 最近 20 条 | 原候选决策流程 | 无显式记忆 |
| G1 | 完整历史加相同预算与压缩 | 原候选决策流程 | 无显式记忆 |
| G2 | 与 G1 相同 | ReAct | 关闭 |
| G3 | 与 G1 相同 | 原候选决策流程 | 开启 |
| G4 | 与 G1 相同 | ReAct | 开启 |

G1 与 G0 比较上下文管理；G2 与 G1 比较工具循环；G3 与 G1 比较记忆；G4 与 G2、G3 比较组合收益。所有组使用相同业务权限、数据、买家目标、卖家模型配置和预算协议。

动态交互不再保证逐句买家输入相同；回复改变后的不同路径就是测量对象。固定场景目标、模拟器版本、模型参数和随机种子，重复运行并报告波动，不能宣称仅靠 seed 即可让真实模型完全确定。

初始规模：先做 20 个场景、每组 3 次重复的确定性或可控模拟模型验证；付费真实模型批次在协议和费用预算冻结后显式执行。扩充到正式样本集时，再根据差异与置信区间决定规模。

### 12.5 指标

| 类别 | 指标与口径 |
| --- | --- |
| 授权 | 未授权承诺、底价泄露、过期报价生效、跨会话访问、重复写入 |
| 协商 | 可达成场景意向达成率、有效结束率、达成时卖家净收益 |
| 交互 | 明确问题未回答率、重复询问率、事实错误率、条件变更处理正确率 |
| 工具 | 参数有效率、无关调用率、相同状态下无信息增益的重复评估率 |
| 记忆 | 来源有效率、旧条件替代正确率、未解决问题跟踪率 |
| 系统 | 卖家运行失败率、恢复成功率、评测买家失败率 |
| 成本 | 卖家模型、摘要、记忆与模拟买家的 Token、费用、调用数和延迟分别汇总 |

“可达成场景”由环境事先判断双方硬约束存在交集；它不等于任何买家都应该被说服。净收益只比较条件相近的达成样本，并同时报告达成率，避免只留下高价成功样本。

事实、权限和最终状态采用程序判定；自然度与说服力先固定评分标准并人工盲评，可将校准后的 LLM 评分作为辅助。意向达成仍然不是支付或实际成交。

费用和耗时报告包含失败调用及维护开销。卖家侧交互延迟与离线评测总耗时分开统计。

## 14 历史迁移与切换

1. 新增表和 nullable source_agent_message_id，不删除现有数据。
2. 为每个会话建立上下文缓存行。
3. 按现有 messages 顺序导入历史公开记录，写入完整流并建立关联。
4. 已有模型任务的输入和结果保留原始格式，不伪造过去不存在的工具轨迹或系统提示词。
5. 导入时标识 LEGACY；无法确定的旧提示词版本保持未知。
6. 所有新公开消息写入入口启用原子投影，即使会话仍运行 V3。
7. 回填后核对公开消息数量、文本、角色、请求标识和关联唯一性。
8. V4 按配置和会话启用，模式在任务创建时冻结，活动任务不切换运行时。
9. 验证完整 V4 Agent 的协商闭环、业务约束、运行可靠性、回复质量、耗时与费用，达到预先明确的使用要求后扩大范围。组件对照用于诊断，不要求先超过尚不完整的 V3。

回退将新任务切回 V3 执行模式；V4 任务在对应 Runtime 下完成或安全终止。已提交的业务动作不撤销，消息流与公开投影继续保存。不能让 V3 Worker 把 V4 快照按旧 Schema 解释。

## 15 分阶段实施与验收

| 阶段 | 交付 | 验收 |
| --- | --- | --- |
| 0 契约与模型能力 | 消息协议、结束契约、预算及 Qwen 工具调用验证 | 调用与结果回传、错误反馈、最终结构化结束可工作；既有 V3 基线保持 |
| 1 完整消息流 | 新存储、公开投影、历史回填、步骤与请求记录 | 无重复买家输入；公开文本与原消息一致；内部轨迹不出现在买家接口 |
| 2 上下文管理 | 完整历史、Token 检查、增量摘要、协议验证 | 每次请求符合预算；工具交互完整；摘要不删除原始流；来源范围可复现 |
| 3 协商记忆 | 结构化记忆、来源校验、条件替代和增量更新 | 超过旧 20 条窗口仍能跟踪明确诉求；撤销条件不继续生效；会话隔离正确 |
| 4 ReAct Runtime | 自主工具选择、反馈调整、终结动作和步骤恢复 | 工具拒绝后能改方案或澄清；恢复不重复提交；租约和版本防护通过 |
| 5 动态买家 | 环境硬约束、实际回复交互、G0 至 G4 分组 | 隐藏目标不进入卖家上下文；模拟器失败单列；评测与生产工具结果一致 |
| 6 效果验证与切换 | 完整任务验收、冻结实验、报告、门禁及回退 | 完整协商任务与业务约束通过验证；可靠性、回复质量、耗时和费用满足预先明确的使用要求；运行模式可切回 |

不预先承诺达成率或费用一定改善。项目主验收以完整 Agent 是否能完成协商任务为依据，覆盖自主工具循环、长上下文与条件记忆、业务执行与恢复，以及绝对可靠性、回复质量、耗时和费用。V3 尚不完整，G0 至 G4 的同条件实验保留为组件诊断，不能代替完整项目验收。实验门禁通过也不自动等于日常使用验收通过；使用阈值应在验证前确定，不根据已有结果调整。

### 15.1 必须覆盖的验证场景

- 20 条以内历史、超过 20 条历史，以及很少消息但内容很长的输入。
- 同一条买家消息不会因全量读取与追加而重复。
- 多个工具调用及各自结果可以正确还原；压缩不产生孤立工具消息。
- 正式承诺来自已提交结果；一个运行最多成功执行一个终结写动作。
- 包邮成本未知时先澄清，不能凭模型估计写入正式条件。
- 买家改变配送偏好或预算陈述后，旧记忆被替代。
- 摘要失败、记忆提取失败、Token 估算偏差和预算耗尽均有明确路径。
- Worker 在模型返回、工具调用保存、写动作提交和 HTTP 返回之间中断后可恢复。
- 旧租约 Worker 不能追加有效执行步骤或提交业务动作。
- 审批、商品或策略在循环中变化时，过期候选被阻断。
- 当前运行使用冻结提示词，新运行才应用新版。
- 动态买家根据不同回复产生相应动作；确认必须指向环境中的有效报价。
- 评测中所有卖家请求、摘要、记忆、买家请求与失败费用被正确归集。

阶段性验证运行现有 Pytest、Ruff、前端类型检查和既有确定性门禁，再增加相应契约、恢复与动态环境测试。真实模型与数据库验证在有对应配置和明确预算的实验阶段运行，不能仅凭离线指标宣称生产并发与数据库一致性通过。

## 16 第一批的完成定义

第一批完成时，主协商 Agent 能在有限循环中自主选择工具，依据结果调整方案；完整消息流可追溯输入、工具交互、实际上下文和最终回复；上下文不再受固定 20 条限制；协商记忆有明确来源并能处理条件变化；动态买家基于实际回复交互；生产授权与任务恢复沿用同一规则。

对外可展示一条真实执行轨迹，例如“读取原始历史中的自提诉求，评估原方案，收到不授权结果，转而澄清面交地点”。效果说明优先报告完整 Agent 的任务完成情况、失败原因、回复质量、耗时与费用，并明确证据范围。冻结的 G0 至 G4 对照用于辅助分析组件贡献；未证明的收益不宣称改善，模拟意向达成不称为真实成交。
